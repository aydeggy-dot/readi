# M2 handover — content model, admin CMS, seed content

**Date:** 2026-09-22 · **Branch:** `feat/m2-content` (stacked on M1; not pushed) ·
**Status:** done, reviewed, awaiting the owner's end-to-end check and pull request

## What was built

**Phase 1 — the content model (ADR-0014 decisions 1–4).** Prisma models for Topic, Track,
TrackTopic, Module, Lesson, Rubric, RubricCriterion, Question, ContentFlag and ContentVersion; the
`draft → in_review → published → retired` workflow as one pure function; `content_versions` as a
single history table; authorship columns as plain uuids with no foreign key; and the Zod contracts,
with the candidate shapes deliberately separate from the admin ones.

**Phase 2 — the service, the APIs and the leak test.** `ContentService` with every mutation as one
transaction (row + version snapshot + audit entry), a snapshot written only when the content
actually changed, keyset-paged admin lists, the candidate reads behind `/api/content/*`, and
`content-no-answer-key.int.spec.ts` — which reads the endpoint list out of the OpenAPI document and
asserts over the raw JSON of every candidate GET that no rubric, criterion, level descriptor or
ideal point appears at any depth.

**Phase 3 — embeddings and near-duplicates (ADR-0006).** An `EmbeddingProvider` adapter in the
worker (Voyage plus a deterministic fake), 1024-dim pgvector column with an HNSW index, embedding on
publish, a cosine-similarity warning that is never a refusal, all raw vector SQL confined to
`question-embeddings.repository.ts`, and the `content:reembed` CLI with its runbook.

**Phase 4 — the seed format, the importer and the first drafted bank.** A YAML format that refers
to itself by slug, may declare only `status: draft`, and carries `author` and a required
`reviewer_notes` per question; a loader that reports every problem with file, line and column; an
importer that writes through `ContentService`, skips anything unchanged, and never deletes,
publishes or embeds; and 14 topics, 3 tracks, 5 modules, 10 lessons and 14 questions with 11
rubrics, all `status: draft` / `author: ai_draft`, with printable review pages for the experts.

**Phase 5 — the CMS, and the source of truth after import (ADR-0014 decision 5).** The `(admin)`
route group in Margin: lists with a no-JavaScript filter bar and keyset paging, create/edit forms,
the rubric editor with a live weight total, markdown preview (dynamically imported, so no candidate
route loads it), status transitions drawn from the same table the API enforces, version history, and
duplicate warnings. Plus `seed_managed`: the files create, the CMS owns.

**Phase 6 — verification, docs, and the unreviewed-draft guard (ADR-0014 decision 6).** Below.

## Phase 6: nothing a model drafted reaches production unreviewed

The gap the owner asked about: `author: ai_draft` lived only in the YAML. The importer validated it
and left it there, so once content was in the database nothing could tell a model's draft from a
question an expert had written and stood behind. The only thing between an unreviewed draft and a
candidate was an admin remembering which was which.

`seed_managed` could not stand in for it — it answers *who owns the words*, and it stays true after
an expert reviews a bank in the YAML and re-imports, which is exactly the flow `REVIEW.md`
prescribes. A guard built on it would have refused the reviewed content and waved through anything
an admin had typo-fixed in the CMS.

So the four publishable entities gained their own review state:

| Column | What it means |
|---|---|
| `ai_draft_unreviewed` | A model wrote this and nobody has vouched for it. Set by the importer from each seed file's `author`. |
| `reviewed_by_user_id` | Who recorded the review. Plain uuid, no foreign key, tombstoned on erasure. |
| `reviewed_at` | When. |

- **Production refuses** to publish a marked item (`content_unreviewed_ai_draft`) unless the publish
  carries `acknowledge_unreviewed`, which the audit entry records — and records only when it
  actually mattered, so searching for it finds real overrides. Only an admin can publish at all, so
  the override is already an admin's.
- **Development, test and the e2e run never refuse.** M3 is built against the seeded drafts, and a
  guard that blocked that would be the first thing anyone turned off.
- **Marking something reviewed is its own action** — `POST /api/admin/content/:entity/:id/reviewed`,
  open to a content expert as well as an admin. It writes a version snapshot and an audit entry, so
  the history carries who and when, and it refuses when there is nothing to review
  (`content_not_unreviewed`) so a second click never churns the history.
- **Saving an edit does not clear the mark.** A draft that needed no changes would otherwise have to
  be edited before it could be approved, and a one-word typo fix would count as having reviewed the
  whole question, its answer key and every level descriptor of its rubric.
- **Re-importing `author: human` clears it**; re-importing redrafted `ai_draft` text marks it again
  and forgets the stale review, because that review was of words the import replaced.
- The CMS shows an **AI draft, unreviewed** chip on every list row and editor, and the publish
  button explains the refusal and offers the override.
- The migration backfills every row `/content/seed` still owns as unreviewed — `ai_draft` is the
  only author the shipped corpus uses.

Said in prose for the people it affects: `content/seed/REVIEW.md` (for the expert reviewers) and
`content/seed/README.md` (for engineers).

## The M2 review

Five reviewers each took one dimension — authorization and the workflow, the data model and
privacy, answer-key leakage, the seed importer and embeddings, and the web CMS — against the whole
milestone, committed and uncommitted. Every finding was re-verified in the source before anything
was changed.

**One blocker, found independently by two of them, in the phase-6 work itself.**

> **`author: human` in a seed file did nothing unless the words changed too.** `applyChange` asks
> "has the content changed?" before it asks anything else, and `author` is not part of the
> content. So an expert who reads a bank, approves most of it **without rewriting a word**, sets
> `author: human` and re-imports — the exact flow `REVIEW.md` prescribes — got "14 unchanged" and
> kept every mark. In production every one of those questions would still have been refused at
> publish, and the only way through would have been the `acknowledge_unreviewed` override, which
> writes "an admin overrode the guard" into the audit log for content a human actually did review.
>
> My own test had hidden it: it changed the prompt *and* the author in the same import, so it only
> ever exercised the content-changed path. It now has a sibling that changes nothing but `author`.
>
> Fixed by `ContentService.syncSeedReviewState`: when the content is unchanged but the file's
> `author` disagrees with the row's mark, the importer reconciles the review columns alone — no
> version snapshot, because no content moved, and an audit entry, because who vouched for what is
> what the audit log is for. Reported on its own line (`8 marked reviewed`).

## Two findings NOT fixed — they are one decision, and it is the owner's

Both reviewers arrived at the same gap from different directions: **the workflow guards
transitions, but not edits.** Nothing in ADR-0014 says a published row is any harder to change
than a draft, and two paths take advantage of that:

1. **A `content_expert` can rewrite published content.** `updateQuestion` and friends never look at
   `status`, and the CMS draws the editor for any status. An expert changes a published question's
   prompt; candidates see the new wording on the next request. No admin, no transition, no
   `content.question.published` audit entry — only `content.question.updated`. The entire point of
   `publish: { roles: ["admin"] }` is that an admin decides what candidates see.
2. **The seed importer can put unreviewed model-drafted text in front of candidates.** A published,
   seed-managed question whose YAML is regenerated by a model and still says `author: ai_draft` is
   rewritten in place by `pnpm db:seed`. The row is re-marked `ai_draft_unreviewed` — correctly —
   but no transition happens, so the production publish guard never runs. Decision 6's invariant
   ("a model's draft cannot reach candidates in production until a person has vouched for it") is
   defeated by a path that never publishes anything.

I have not guessed at this. The options are roughly:

- **(a) Published content is read-only** until an admin returns it to draft. Strictest, and it
  takes content offline to fix a typo.
- **(b) Editing a published row requires `admin`.** One guard, keeps the editorial model, and
  matches "an admin decides what candidates see" exactly. My recommendation.
- **(c) An edit to a published row returns it to `in_review`**, so an admin re-publishes. Safest
  for quality, most disruptive — a typo fix takes the question out of circulation.
- **(d) Leave it, and say so in the ADR** — content experts are trusted staff, and this is an
  insider-trust question, not an outsider one.

Whatever is chosen for (1) should decide (2): if published rows need an admin, the importer should
refuse (or at minimum name) published rows it is about to re-mark, in the same report as the
skipped list.

## Known gaps, recorded rather than fixed

- **The review flow has no UI-level test.** The API behind it has eight integration tests and the
  chip is verified at 360px in both themes, but no e2e drives "Mark as reviewed", and the visual
  capture list has no CMS *detail* page — so `ReviewPanel`, `TransitionPanel`, `VersionHistory` and
  the rubric editor with real criteria are never screenshotted. Adding the e2e is awkward today:
  the e2e database outlives a run and only the importer can create a marked row, so a test that
  marks one reviewed passes once and then silently stops testing. Worth fixing with a reset step.
- **Retiring a rubric silently hides every published question that uses it** — the candidate read
  filters on `rubric.status`, so the questions vanish with no warning at the point of retiring.
- **A question edited while `retired` keeps a vector of its old words**, and `content:reembed` skips
  it because `stale()` filters on `status = 'published'`. It answers duplicate searches with the
  old text's vector and the new text's prompt until it is published again.
- **`markReviewed` writes a version snapshot identical to the one before it** — review state is not
  part of the snapshot, so only the change note ("marked reviewed") distinguishes it. Deliberate:
  the owner asked for the review to appear in the version history, and the version row carries who
  and when.
- **The migration backfill used `WHERE seed_managed`**, so an AI draft already typo-fixed in the CMS
  was treated as vouched-for. There are no such rows in any database today (all 38 seeded rows were
  untouched, and production has no content), but the faithful predicate was `created_by_user_id IS
  NULL`.
- `@@index([type, difficulty])` on `questions` serves no query in the codebase.
- `SEED_ACTOR` is now only used as a default; the importer builds a per-file actor.
- The transition endpoint returns 201 while documenting 200. `markReviewed` returns 200.
