# M2.5 handover — roles, levels and stacks become content

**Date:** 2026-09-22 · **Branch:** `feat/m2.5-roles` (cut from `main` at `833e3fa`; not pushed) ·
**Status:** done and reviewed, awaiting the owner's end-to-end check and pull request

## What the milestone was for

`frontend | backend | qa` and `intern_junior | mid` were one constant in
`packages/shared-types/src/constants.ts` copied into four more closed sets that all had to agree: a
Zod enum, two Postgres enums (and two enum **array** columns), a generated Pydantic `Literal`, and an
i18n namespace whose message keys *were* the enum values. Adding a role meant a change in five
artefacts, a migration and a deploy — in a product whose growth story is "more roles", and whose
catalogue names eighteen of them.

M2.5 made the three of them content. **ADR-0015** is the decision; `docs/role-catalogue.md` is the
plan for which roles come next.

## What was built

**Phase 1 — the catalogue exists, beside the enums.** `CareerRole`, `CareerLevel` and `Stack` as
publishable entities with the full ADR-0014 column set (status, version, `content_versions`, audit,
`seed_managed`, review state); `CareerRoleLevel` and `CareerRoleStack` join tables carrying display
order; `ContentService` CRUD and transitions for all three; publishing a role refused without a
published level; retiring refused while in use; the admin routes and the candidate read
`GET /api/content/career-roles`; `roles.yaml`, `levels.yaml` and `stacks.yaml`, imported before
anything that references them.

**Phase 2 — the CMS.** Roles, Levels and Stacks sections in `/admin/content` with the same
no-JavaScript filter bar, keyset pager and review/transition/version panels as every other entity;
`career-role-form.tsx`, where a role's levels and stacks are part of the role rather than
sub-resources; order preserved on save (`catalogue-order.ts`), so opening a seeded role and pressing
Save does not reshuffle a candidate's picker; at most one default stack, as a radio group in the form
and a refine in the contract.

**Phase 3 — the switch.** One hand-written migration (`20260922145408_catalogue_switch`) that adds
nullable, backfills, `RAISE EXCEPTION`s naming any row that did not map, sets `NOT NULL` and only
then drops — because Prisma's own version refused to run and would have dropped six columns' worth of
data. Both Postgres enums gone; `Track.roleId/levelId`; `Profile.targetRoleId/targetLevelId`;
`QuestionCareerRole` / `QuestionCareerLevel`. `TARGET_ROLES` and `EXPERIENCE_LEVELS` deleted, the
`targetRoles.*` and `levels.*` i18n namespaces deleted with them, and every label now the `name` on
the row the API returns.

**Phase 4 — the stack dimension.** `question-eligibility.ts`: `isOfferedToStack` (pure) and
`stackFilter` (the Prisma fragment) next to each other, because two expressions of one rule fail by
drifting apart. `QuestionStack`, `Profile.targetStackId` (`RESTRICT`), `Profile.stack` renamed to
`technologies`, the onboarding stack picker, the CMS stack filter, and `stack_label` on the CV
contract. A candidate who chose no variant is offered the general questions only.

**Phase 5 — the proof and the docs.** Below.

## The acceptance criterion, and how it was tested

> Add a fourth role end to end — levels, stacks, questions tagged, visible in onboarding and in the
> practice list — **with no code change and no migration**.

Done, with **Full-stack engineer**:

1. Four rows in `content/seed/stacks.yaml` (React + Node, Django + React, Laravel + Vue, .NET +
   React; Next.js and Ruby on Rails are the rows frontend and backend already offer — a stack belongs
   to as many roles as offer it).
2. One block in `content/seed/roles.yaml`: two levels, six variants, React + Node as the default,
   `supported_question_types: [technical, scenario, behavioral]`.
3. `fullstack` added to the `roles:` list of **eleven of the fourteen** seeded questions — the eight
   frontend and three backend ones. The three QA questions were not tagged: a QA interview is not
   part of a full-stack interview. Nothing was copied; the many-to-many link is the point.
4. The two React questions also gained the **React + Node** variant, so the stack rule could be seen
   working on the new role rather than only in a test.
5. `pnpm db:seed` → 1 level, 4 stacks, 1 role created and 8 questions updated. The three questions
   already published in the dev database were **left alone and named**, exactly as ADR-0014 decision 7
   says; `-- --force` was the way through here, and editing them in the CMS is the path on a database
   with real candidates.
6. An admin published the four stacks and the role in `/admin/content`, by hand, at 360px.

**What a candidate then sees.** Onboarding offers four roles. Choosing Full-stack draws its six
variants in the role's order, React + Node preselected, "Not sure yet" last.
`GET /api/content/practice` for a **mid, React + Node** candidate returns four questions —
`api-error-shape` and `n-plus-one-diagnosis` from the backend bank, `react-state-placement` and
`react-unnecessary-effect` from the frontend one. That single response is the argument for the role.
The same candidate switched to **Laravel + Vue** is offered the two backend questions and neither
React one.

**`git diff` over `apps/` for the role itself: nothing.** No migration ran.

**The one thing full-stack does not have is a track.** `GET /api/content/track` answers
`track_not_found` for a full-stack candidate, because tracks are keyed by role and level and nobody
has written one. That is content, not a defect — the track and the boundary questions (where logic
belongs, data flow across the boundary, deploying a whole feature) are the question-bank pass,
`docs/plans/content-catalogue-banks.md` — but it is the one place the role is visibly thinner than
the three it was built from, and the first thing to fix if full-stack is demoed.

## The one code change the proof itself needed, and why it is not the role's

"No code change" is a claim that only means something if the exceptions are stated, so: adding the
role, its variants and its question tags touched no code. Two things in the same phase did, and
neither is the role's.

**The review pages never named which roles a question is for**, and `REVIEW.md` now asks reviewers to
confirm exactly that ("does this question belong to full-stack as well?"). So
`apps/api/src/content/review-doc.ts` prints `roles: …` in each question heading, with a unit test —
`review-doc.spec.ts`, the first for that file. The catalogue did not need it; the new reviewer
question did.

**The landing copy names the roles in prose** — "Frontend, backend and QA" — in two places, so a
fourth role was a copy edit there. That is the right trade today and the wrong one by wave 2;
`tasks/todo.md` has it as an M10 item.

The milestone **review** that followed changed a good deal more code, which is what a review is for.
It is a separate section below.

## Decisions taken in this phase

- **The slug is `fullstack`**, not `full-stack`: it matches `frontend`, `backend` and `qa`, and it is
  the spelling `docs/plans/content-catalogue-banks.md` already assumes. The display name is
  "Full-stack engineer".
- **All eleven transferring questions were tagged, not a token two.** The catalogue's argument for
  full-stack is that it costs near-zero content; tagging only some of what transfers would have made
  the role worse than the argument for it.
- **`senior` was added as a draft level that no role offers.** Adding the row costs nothing and
  proves the claim again; offering it would put a level in the picker with no content behind it. The
  content it needs — system design as a question type, rubric dimensions for scope and influence,
  longer sessions — is recorded in `tasks/todo.md` § Carried forward with the milestones it touches.
- **The M3 plan was brought onto the catalogue now** rather than left for M3 to trip over: the ten
  edits the M2.5 plan listed under "What the saved M3 plan must change" are applied, including the
  transport ADR renumbering to **0016**.

## The milestone review

Four reviewers over `git diff 833e3fa`: authorization and privacy, schema and migrations, contracts
and the worker, the web and the docs. The full list, including what was deliberately **not** fixed,
is in `tasks/todo.md` § "M2.5 milestone review". The two that mattered:

- **A candidate could set their profile to an unpublished level.** The role was checked for
  `published` and the stack was checked for `published`; the level was not, although the method's own
  docstring claimed all three. Reachable the moment a role lists a level before that level goes out —
  which is how a ladder is extended, and exactly what `senior` now is.
- **Publishing a question whose catalogue tags were all still drafts made it invisible to everyone.**
  Nobody can choose a draft variant, so such a question is published, looks published in the CMS, and
  is asked of nobody: the M2 rubric failure ("retiring a rubric silently hid every published question
  that used it") on three new axes. Publishing is refused now, and the guard's first act was to find
  seven questions in a test fixture already in that state.

Also fixed: three CMS error codes with no copy (and a new test that reads the codes out of the API's
source, which found two more); `stackFilter` returning a bare top-level `OR` that M3 would have
silently broken by composing with its own; the seed files being able to break rules only the HTTP
contract enforced; the role editor having no way to express "no default"; `aria-invalid` and error
text that was orphaned in the DOM; and the onboarding e2e asserting a row **label** where it claimed
to assert the chosen value.

Six findings were recorded rather than fixed, each with the decision it needs. The one to read before
deploying anything: **`20260922145408_catalogue_switch` cannot run on a database that already has
rows but no catalogue**, and the fix must not be an edit to the applied migration.

## What M3 inherits

1. **The question-selection rule already exists.** `question-eligibility.ts` holds the pure predicate
   and the Prisma filter; M3 reuses both rather than writing a third expression of the same rule.
2. **The session must pin versions of five things**, not two: question, rubric, **role, level and
   stack** — they are versioned content now, so renaming a role after a session would otherwise
   change what a past report says it was.
3. **Interview types are per role** (`CareerRole.supported_question_types`), so "a preset mixed
   session" means mixed per that role.
4. **The setup screen reads `GET /api/content/career-roles`.** There is no `TARGET_ROLES` to import.
5. **Test fixtures mint their own catalogue rows.** The `(role, level)` pair-ownership scheme is gone.
6. **The worker is sent labels, not keys**, and a staff-written label is wrapped as data.
