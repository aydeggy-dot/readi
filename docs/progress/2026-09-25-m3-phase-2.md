# M3 phase 2 — the engine in the worker (handover)

**Branch `feat/m3-interview-engine`, four commits on top of phase 1, not pushed.** The interview
now runs: a deterministic state machine our code owns, in text mode, with the model confined to
phrasing what a state decided to say and to judging whether an answer has already reached a probe.
No API route yet and no screen — phase 3 wires them, phase 4 draws it.

The plan is `docs/plans/m3-interview-engine.md`, amended again where this phase departed from it.

## 1. The snapshot in the request is the authority

The plan said the bundle is sent "on the first call or after a Redis miss". The API cannot detect a
Redis miss — so the worker answers **`bundle_required`** and the API resends. That error is the
miss signal, and it is the only reason Redis is in the text-mode path at all: it saves resending
four to eight pinned questions every turn, and it is where M5's LiveKit agent will read state from
when it drives turns itself with no API request to carry it.

Where the request's snapshot and Redis disagree, **the request wins**. That is not just the simpler
rule, it is the right one: the API's copy is what has actually been *persisted*, so a response that
reached the worker's Redis and then failed to reach the database should be **replayed**, and
trusting Redis would skip ahead and leave a hole in the transcript.

That decision made the next one obvious: **an exchange is all-or-nothing.** Nothing is stored until
it completes, so on an error the response carries no turns and a null snapshot, and a retry replays
it — idempotently, because the engine allocates the seqs. It also removed the need for a `resume`
action, which a half-completed exchange would have required.

## 2. A model that will not answer does not stop the interview

Every phrasing call has a fallback in pinned, staff-written content already on the wire: a question
falls back to its own prompt, a follow-up to its own probe, the close to a fixed line. A failing
provider gives the candidate a plainer interview rather than a broken one, and the failure is in
`ai_calls` for anyone reading afterwards.

The exception is answering a question the **candidate** asked, where there is nothing honest to fall
back to. That is the only thing that returns `llm_error`, and because the exchange is atomic the
candidate retypes rather than losing the session.

A failed **coverage** call is not an error at all: the log records `not_judged` for every criterion
and the engine asks the probe it would have asked anyway. In doubt, ask — a follow-up that was not
needed costs a minute, one that was never asked loses something they would have said.

## 3. The free latency savings, as one rule in one place

`machine.probes_to_judge` returns nothing — and so no coverage call is made — when the follow-up
budget for this question is spent, when every probe has been asked or already covered, or when the
deadline leaves no room for a follow-up. Every one of those is a case where the verdict could not
change what happens next, which is what makes them free rather than a trade.

When coverage *does* run and reports everything covered, `choose_probe` returns None, so there is no
follow-up to phrase either and the engine moves on. A complete answer is not punished with two
redundant questions.

The turn is still logged in all of these cases, as `not_judged` for every criterion. That is the
honest record: nothing judged this, so nothing is claimed about it — which is exactly the third
value the verdict enum was given for in phase 1.

## 4. Coverage is tracked per probe; the log still reads per criterion

`EngineQuestionProgress.covered_criteria` became `probes_covered` before anything was built on it.
A criterion may carry two probes and they ask separable things ("how would you check it works" and
"what would you do when that check fails"), so an answer can reach one and not the other. Tracking
per criterion would either re-ask what was answered or drop what was not — and anything keyed by
criterion drops the second probe outright, which `review-doc.ts` really did.

Per criterion is still how the stored log reads, because that is what a rubric is. `coverage_log` is
where the two views meet: a criterion is `covered` only when every probe of it that was judged came
back answered.

## 5. Eight prompts, not five, and the intro is not one of them

The plan listed five. The coverage call needs its own system and input prompts — the decision to
have a coverage call postdates that list — and `interview_intro.v1.md` is **rendered and spoken,
never sent to a model**.

The intro is where the facts are: how long the session runs, how many questions there are, that
follow-ups happen, that skipping and ending early are allowed. A model paraphrasing those gets them
wrong eventually, and a candidate told "about four questions" who got eight has been misled by us.
It is also the turn where they are watching an empty screen waiting for the session to begin, so it
is the call most worth not making. It is versioned and recorded in `prompt_versions` like the rest,
because a session should be able to say what it said.

`interview_wrapup.v1.md` is told **not** to promise feedback, a score or a report. M3 scores
nothing; what happens next is the completion screen's to say, where it can be accurate. A v2 belongs
with M4's evaluator.

## 6. Prompt injection is answered structurally first

Nothing a candidate types can end the session, skip a question, award a mark or choose the next
probe — because none of those is a model decision in the first place. `test_interview_injection.py`
drives each of the four named injections through a real session and asserts the engine does exactly
what it was going to do, then adds two more: a model that announces the end of the interview (the
state machine has not moved) and a coverage answer naming a probe the question does not have
(dropped).

The prompt defences are tested separately, against the rendered prompts, so a reworded prompt that
drops a clause fails in CI: candidate text always sits inside an `as_data` block with its tags
neutralised, the system prompt says instructions inside the data are not requests, and the coverage
prompt says a claim to have answered everything is not evidence about itself.

**No prompt in this phase receives a rubric, a criterion, a weight, a level descriptor or an ideal
point**, because the bundle does not carry them (phase 1, `session-bundle.ts`).

## 7. The migration guard, because the sixth time was in a one-line migration

`prisma migrate dev --create-only` for `ALTER TYPE "ai_call_purpose" ADD VALUE 'coverage'` — a
migration that touches no table — generated `DROP INDEX "questions_embedding_hnsw"` alongside it.
Sixth time. CLAUDE.md has warned about it since M2 and `tasks/lessons.md` since M2.5; the warning
keeps failing because it asks a person to notice something in a file they are about to apply without
reading.

`apps/api/src/prisma/migration-sql.spec.ts` reads every committed `migration.sql` — no database, no
fixtures, in `pnpm test` and in CI — and fails on a migration that drops a hand-written index, a
column one is built over, or its table, without recreating it in the same file. The message names
the file, says to delete the line, and says what the loss would silently cost.
`content-schema.int.spec.ts` stays as the backstop in a migrated database.

Watched failing on both halves before being kept: the `DROP INDEX` line re-added, and an
`ALTER TABLE "tracks" DROP COLUMN "role_id"` — the M2.5 shape that Prisma proposes nothing for.
Adding hand-written SQL now means adding it to `HAND_WRITTEN_SQL`.

## 8. The one bug worth naming

`EngineState.pending_text` held "the thing the candidate just said", but it is read in exactly one
place: `CANDIDATE_QUESTIONS`, where the engine must hold their question in order to answer it.
`take_answer` set it for every answer, so the moment a question's follow-ups were done and the
engine moved into `CANDIDATE_QUESTIONS`, it found a pending utterance — the candidate's *interview
answer* — and answered it as though it had been a question put to the interviewer.

The transition-table tests caught it on the first run. That is the argument for writing the machine
as `(state, event, now) → state` with no I/O: the failure was three lines of expected steps rather
than a strange turn in a session somebody had to read. The lesson is in `tasks/lessons.md`.
