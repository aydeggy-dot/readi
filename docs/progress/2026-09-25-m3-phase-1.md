pushed.** The API half of the interview engine, before a word is spoken. No LLM, no engine, no

## 1. A question exists at three widths

This is the shape worth carrying into phase 2, because the gaps between the three are the product
rules rather than an accident of convenience. `apps/api/src/interviews/session-bundle.ts` is the
only place they are crossed, so each rule is a function with a test rather than something to
remember at a call site.

| | Holds | Goes to |
|---|---|---|
| `SessionQuestionSnapshot` | prompt, context, ideal points, the rubric's criteria, planned follow-ups | nowhere — stored on the session |
| `BundleQuestion` | prompt, context, planned follow-ups, `criterion_count` | the worker |
| `CandidateSessionQuestion` | prompt, context, type, topic | the browser, and **only once asked** |

**The bundle carries no rubric**, and that is a correction to the plan. Its architecture paragraph
said the API sends "the pinned questions with their rubric criteria" — written before the
owner's decision of 2026-09-23 and contradicting it, because if the criteria cross then the answer
key is back in every interviewer-model call. The worker phrases a probe the engine chose and judges
whether an answer already covered one; neither needs the criteria, the weights or the descriptors.
`criterion_count` crosses instead: enough for the coverage log to say "criterion 2 has no probe, so
nothing judged it", not enough to score. The rubric reaches the **evaluator** in M4, from the
snapshot.

**Only questions the session has reached** reach the browser. Reading ahead is not a leak of the
answer key, but it is a leak of the interview: a candidate who can see question four while answering
question one is preparing rather than being interviewed. `asked_at` is the gate.

One decision phase 2 inherits, recorded in the plan: **coverage is judged against the probes, never
against the rubric**, and its verdict is `covered | not_covered | not_judged` rather than a nullable
boolean. `not_judged` is the ordinary state of the one criterion the opening prompt asks for, since
nothing probes it, and a stored log should say that rather than leave a reader to decode a `null`.

## 2. `interview_sessions.catalogue`, and why a version was not enough

The carried-forward item said to pin the question and rubric **versions**. Writing the pinning test
showed that is half the guarantee: a version pins what the content *said*, not what the row was
*called*. Roles, levels and stacks are versioned content (ADR-0015), so renaming a role to "Backend
developer" would have silently rewritten every past session's report to say something the candidate
never saw — and the plan's own acceptance criterion is "rename the role afterwards; the report still
says what it said".

So the session carries a `catalogue` column: the slugs and names as they read at session time. The
FKs and versions stay for joins and analytics; the column is what the session *says it was*, and is
what the response, the list and the export all read.

`interview-pinning.int.spec.ts` edits the question, reweights the rubric and renames the role through
the admin API an admin really uses, then asserts nothing moved. **It was watched failing on both
halves independently** — once reading the live question instead of the snapshot, once reading the
live role name instead of the catalogue — before being kept.

## 3. What the data export leaves out, and why

A transcript is the candidate's own words, so the export carries every session, the questions as
they were asked, and every turn. It deliberately does **not** carry `follow_up_index` or
`criteria_covered`.

Both are positions in a rubric the export does not contain, so they are meaningless without the
answer key and misleading with it: "criterion 1 was not covered" tells a candidate they missed
something without telling them what, and telling them what would be handing over the rubric. What
they are owed about how they did is the rubric-based report (M4), which cites their own words back
to them; what they are owed here is their words.

**This is the one judgement call in the phase** and it is reversible — say so and it goes in.

## 4. The test bug a warm database had been hiding since M2.5

M3's schema change meant dropping `readi_test`. The suite then failed **13 tests** in
`content-seed.int.spec.ts`, and none of them were mine.

That spec builds a temporary seed directory whose question says `roles: [frontend]`, `levels: [mid]`
— rows no file in that directory defines. The importer resolves them from the database, so the block
passed for as long as some other spec, or some earlier run, had already imported the real corpus.
On a genuinely empty database, which is what CI creates every run, it fails with
`SeedReferenceError: … names role frontend, which no seed file defines`.

Confirmed identical on `main` in a worktree before changing anything. The fixture defines its own
role and level now and borrows nothing (`bc97dd1`, committed on its own).

The general lesson is in `tasks/lessons.md`: the M2.5 rule — "a test that names content it does not
create is borrowing" — has a second half. **Drop the test database and run the suite before
believing it is green.** A suite that has only ever run against a database with history in it is a
suite with an unknown number of these.

## 5. `prisma migrate dev` cannot apply an edited migration here

CLAUDE.md says to generate with `--create-only`, edit the SQL, then apply. Applying it with a second
`prisma migrate dev` hangs — silently, for the rest of the session.

The cause is the hand-written HNSW index. Prisma cannot see an index over an `Unsupported` column,
so the schema and the shadow database never agree: every `migrate dev` diffs them, finds an index it
wants to drop, and asks `Enter a name for the new migration:`. With no terminal it waits for ever,
holding `pg_advisory_lock(72707369)` throughout. A process from the 2026-09-23 session had been
sitting on that prompt for **twenty hours**.

The damage lands on the *next* run, which fails with `P1002 … The database server was reached but
timed out` — an error that sends you to `docker ps` and connection settings rather than to the
prompt. `select * from pg_locks where locktype='advisory'` names the pid holding it; terminating
that backend frees it.

**Use `prisma migrate deploy` to apply an edited migration.** It applies what is pending without
diffing, so it cannot prompt. CLAUDE.md §5 says so now.

(The same migration also contained `DROP INDEX questions_embedding_hnsw` for the **fifth** time, in a
change that only creates three tables. Deleted; both hand-written indexes verified present after
applying.)

```bash
pnpm lint && pnpm typecheck           # clean

                                      # regeneration as drift
pnpm test                             # 420 API · 120 web · 93 shared-types · 77 Python · 56 ui · 3 api-client
```

The API suite was run against a database **created from scratch**, not a warm one. `pnpm test:e2e`
belongs to phase 6 and has not been run.

Two further controls worth knowing were exercised by hand and then reverted: the widened leak test
was proved to catch an interview leak by adding `planned_follow_ups` to `CandidateSessionQuestion`
and its mapper (it failed on both the marker text and the field name), and an earlier attempt at
that control — adding an undeclared field to the response — proved nothing, because
`ZodSerializerDto` strips it before it reaches the wire.
