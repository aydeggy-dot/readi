# M3 phase 3 — wiring (handover)

**Branch `feat/m3-interview-engine`, six commits on top of phase 2, not pushed.** The engine and the
API are joined: a candidate's session can now be advanced over HTTP, the transcript is written down,
and every model call is billed to the session. There is still no screen — phase 4 draws it.

The plan is `docs/plans/m3-interview-engine.md`. The transport decisions are
`docs/adr/0016-interview-transport-and-streaming.md`.

## 1. The stream was proved before anything depended on it

`scripts/sse-rewrite-proof.mjs`, run first, before the route existed.

The browser reaches the API same-origin through Next's `/api/*` rewrite, so every frame passes
`proxy.ts` — which matches `/api/:path*` — **and** the rewrite, and `next dev` and `next start` are
different code paths. A stub origin emits five frames 300 ms apart behind a production `next start`;
a client reads them through the web origin and times each arrival:

```
status            200
content-type      text/event-stream
content-length    (absent)
transfer-encoding chunked
frames arrived at 330, 624, 925, 1225, 1527 ms
```

One frame per gap. Nothing buffers. It is isolated on purpose — a stub origin rather than the real
API, so a failure is Next's buffering and nothing else — and it is committed rather than written up,
because a Next upgrade could change the answer and a note cannot fail.

Two things it cost, both now in `tasks/lessons.md`: `server.close()` waits for keep-alive
connections the readiness probe left behind (so the script hung *after* reporting, and because its
output was piped through `tail`, nothing printed at all), and `pnpm exec next start` leaves
`next-server` as a grandchild holding the script's stdout open for ever.

## 2. What exists

| Route | |
|---|---|
| `POST /api/interviews/{id}/advance` | One exchange, `text/event-stream`. Frames: `thinking`, `turn`, `question`, `state`, `error`, `done` |
| `GET /api/interviews/{id}/status` | What the completion screen polls |

Behind them: `InterviewAdvanceService`, `InterviewStream`, `applyExchange` on the repository,
`advanceInterview` on `AiWorkerClient`, and `FakeInterviewEngine` as the test double.

**What SSE buys in M3, stated honestly.** Not incremental generation: the worker answers a whole
exchange at once, so the turns arrive together. It buys the `thinking` frame sent *before* the model
call, so the screen shows the interviewer composing the instant the candidate presses send; a
heartbeat (`INTERVIEW_SSE_HEARTBEAT_MS`) while a call is in flight, which keeps whatever sits between
the API and a mobile browser from closing a connection it thinks is idle **and** tells the screen the
difference between "still composing" and "we have lost you"; and a channel M5 reuses unchanged.

**Where a refusal appears depends on when it happens.** Everything knowable before the stream opens
is an ordinary `ApiError` with a status — `interview_not_found`, `interview_ended`,
`interview_expired`, `interview_busy`, request validation. Once the headers are out the status is
already 200, so a failure after that is an `error` frame. Nothing between `open()` and `close()`
throws.

## 3. An exchange is all-or-nothing, and what follows from it

Neither side stores anything until the worker has answered in full. A broken stream, an API timeout
or an unreachable worker leaves the session exactly where it was, and the same action is simply sent
again — replayed idempotently, because the engine allocates the turn seqs.

Two consequences in the code:

- `applyExchange` upserts turns by `(session_id, seq)` with an empty `update`: what was said was
  said, and its timing belongs to the exchange that really produced it.
- `follow_ups_asked` is **recounted from the transcript** rather than incremented. An increment is
  right once and wrong on a replay, and the transcript is the record. `asked_at` is set only where it
  is null, so a replay reports no newly asked questions and streams no duplicate `question` frame.

There is a test for this that does not rely on the double misbehaving: it takes the response the
worker really gave, applies it a second time, and asserts the transcript did not move.

## 4. The Redis miss the API cannot see

The bundle — four to eight pinned questions with their setup material — goes out on the first
exchange and then not again; the worker caches it. When that cache has gone the worker answers
`bundle_required`, which is the **only** way the API can learn of a Redis miss inside another
process, and the exchange is retried with the bundle. That answer costs no model call, so only the
retry spends anything.

Where the API's stored snapshot and the worker's Redis disagree, the request wins. The API's copy is
what has actually been *persisted*, so replaying an exchange whose response reached Redis and not the
database is right, and trusting Redis would leave a hole in the transcript.

## 5. `AI_WORKER_TIMEOUT_MS`, re-checked — and the fix was on the other side

The plan asked for the API's timeout to be re-checked for two chained calls. The honest answer was
that the API's timeout is the wrong place. The worker bounded every call at `LLM_TIMEOUT_S` = 90 s,
which is right for a CV parsed in a background job and wrong for a candidate watching a spinner: two
of those chained is three minutes of nothing happening.

So `LLMClient.parse` takes an optional per-call `timeout_s`, and the interviewer passes
`INTERVIEW_LLM_TIMEOUT_S` (45 s) on every call. The normal worst case is then 90 s and
`AI_WORKER_TIMEOUT_MS` (150 s) covers it with room for one retry — deliberately not for the
pathological case, because the API giving up costs a replay, not a session.

## 6. The leak test's rule about probes had to be narrowed, and it caught it

**This is the finding of the phase.** `content-no-answer-key.int.spec.ts` treated a question's
planned follow-ups as answer key and forbade them in every candidate response. Phase 3 built the
route that *asks* one — the interviewer speaks the probe, so the candidate hears it — and the test
failed on the fixture's own marker.

Both easy fixes are wrong. Dropping probes from the marker list loses the check that stops one
leaking through a question's setup material or through a question the session has not reached, which
is the leak that matters, because it tells a candidate what is coming. Exempting the interview
routes exempts the surface with the most to leak.

What it became: **a probe may appear inside the `text` of a turn an interviewer has spoken, and
nowhere else in any payload** — counted, so one occurrence in the right place and one in the wrong
place still fails. That is a stronger claim than the old one everywhere except the single place it
had become false. `plannedFollowUpMarkers` is its own list on the fixture now, and CLAUDE.md §5 is
corrected to match.

Covering the stream needed two other things: an event stream is not JSON, so `response.body` is `{}`
for it and the frames are parsed out instead — with a negative control proving that parsing can
still catch a leak — and the advance route needed its own candidate, because `POST /api/interviews`
is also an exerciser and starting an interview abandons whatever that candidate had running.

## 7. The per-criterion maps, audited

You asked for this and it is worth writing down. There are four places that build a per-criterion
view, and none of them keys probes by criterion:

| | |
|---|---|
| `probes.py::_probes_for` | a list comprehension over `enumerate`, returning every index for that criterion |
| `review-doc.ts` | `Map<number, string[]>` — grouped, not keyed, with `review-doc.spec.ts`'s "prints both probes when a criterion carries two" |
| `check-bank.mjs` | a **count** per criterion, which is what it is checking (at most two) |
| `fake-ai-worker.ts::coverageFor` | a `filter`, and test-only |

`probes.py` also keeps a *set* of criteria that have been probed, which is only used for "prefer a
criterion nothing has probed yet" and cannot lose a probe.

Two new checks so this stays true rather than being remembered:

- `test_interview_probes.py::test_no_per_criterion_view_ever_loses_a_probe` — the general form. Every
  probe is reachable by selection given the budget, and the log has one entry per criterion with two
  criteria probed by three probes between them.
- **The API has no per-criterion view at all**, which is its answer to the same bug. The coverage log
  arrives whole from the worker and is written whole, asserted byte-for-byte against what the engine
  sent, so the one place it could be reshaped is a place a test says does not exist.
