# M4 phase 3 — the job, the scoring rule, the report in code

**Branch `feat/m4-evaluation`. 2026-09-27.** Phase 2 left an evaluator nothing called. This phase
calls it: a session ending queues a job, the job scores every answered question against the content
the session pinned, the arithmetic on top happens in code under `SCORING_VERSION`, and a report is
assembled from the per-answer JSON and stored. There is still no route and no screen — that is
phase 4 — so the report is read from `session_reports.summary` by tests and by nothing else yet.

`tasks/todo.md` carries the checklist and the four open questions this phase answered. This is what a
reader needs that the checklist does not say.

## The four things that shaped it

**A session has more doors out than the plan listed.** The plan named three paths to `ENDED` — budget
exhausted, ended early, the stale sweep. There is a fourth: starting an interview abandons the one the
candidate left (`InterviewSessionsRepository.create`), and that session's answers are just as real.
So all four go through one method and one rule, and both `abandonStale` and `create` now return ids
where they returned a count and nothing. **An abandoned session with answers in it is scored**, which
is a decision rather than an oversight: which door a session left through is invisible to the
candidate, and "sometimes there is a report" is a worse product than one report per set of answers. It
costs a paid evaluation for a session somebody walked away from, and that is the price.

**The prompting adjustment is two decisions, not one.** 0.85 on any non-zero score is the one the owner
took. The one that had to be taken while writing it is that the discount comes off the **numerator
only** — if it came off the weight in the denominator too, a prompted criterion scoring well would
*raise* the total, which is the sort of arithmetic a candidate finds before we do. The unit test for it
asserts `prompted < unprompted` rather than a number, because the number is the thing that could be
wrong.

**"Per probe, never per criterion" is a rule about a data structure, not a style.** A criterion may
carry two probes, and `planned_follow_ups` is a flat list in which two entries may name the same
criterion, so `follow_up_index` is a position in that list and nothing may key a map by criterion —
`review-doc.ts` did and silently under-reported a bank. Here the consequence would have been a *double*
discount, 0.85², on a criterion that needed two nudges. `promptedCriteria` resolves per probe and
collapses to a set at the end, and that is the reading: needing two nudges on one criterion is one
criterion prompted.

**`TrackTopic` has a reader for the first time.** It has been written by `content.service.ts` since M2
and read by nothing. `TrackTopic.isCore` × `Lesson.topicId`, through the published track for the
session's role and level, is what turns "you went worst on databases" into a lesson link. It returns
nothing for five of eight role × level pairs, so the empty state is the part of it that ships.

## The pinning test was wrong, and the mutation found it

The instruction was to extend the pinning test to scoring and watch it fail in both halves. Written the
obvious way — run a session, score it, **then** edit the question and rubric — it passed. Mutated to
weight the criteria from the live `rubric_criteria`, **it still passed**, because an answer that already
has a row is never re-scored: after the edit nothing read a rubric again, and the stale read never
happened. The test was asserting that a stored number stays stored.

It now edits the question's prompt, its ideal points **and the rubric's weights** while the interview is
still running, and then lets the candidate finish. That is also the real sequence — a session runs for
fifteen to thirty minutes and an expert can rework a rubric inside that window — so "pinned" means
pinned at the moment of **scoring**, not at the moment of asking.

Both halves then failed, by hand, on 2026-09-27:

| Mutation | What failed |
|---|---|
| Report assembled from the live `questions` row | the prompt and "what a strong answer covers" |
| Criteria weighted from live `rubric_criteria` | the score — 90 became 10 on content nobody saw |

Under the first mutation **547 other tests passed**, which is the reason that file exists. A second
thing the exercise settled: the fixture scores 4 on the first criterion and 0 on the second, because
with both criteria scoring alike any weighting gives the same number and a weights test whose fixture is
symmetric tests nothing.

## The injection flag, and the four open questions

The owner's decision of 2026-09-27 was to make the line phase 2's gate cannot hold **visible** rather
than to score around it: a model that quotes the injection itself quotes something the candidate really
typed, so it verifies and an inflated score stands. All four open questions are answered in
`tasks/todo.md`; the two worth repeating here:

- **The worker returns the matched phrases**, on `EvaluateAnswerResponse.evidence_flags`, which puts the
  phrase list beside the payloads that motivated it — and the test asserts **both** directions, so a
  phrase added without a case, or a case added without a phrase, fails in CI. That bidirectional check is
  the only thing that keeps a list like this from growing by superstition.
- **Punctuation is kept** when matching, unlike `evidence.py`'s `normalise`. `SYSTEM:` is a phrase;
  `system` is a word most technical answers contain, and a list that flagged every answer mentioning a
  system would be read once and then ignored. The cost — `ignore-the-rubric` would slip past — is one a
  person reading flagged answers can live with and a wrongly flagged candidate could not.

`test_the_gate_does_not_catch_a_real_quote_used_to_justify_nonsense` now asserts the score is still
4/4 **and** that the flag is set, which is what its own docstring asked for: "if this test ever starts
failing because a new guard catches it, that is good news and the guard should be described here."

## What was found on the way

**The enqueue could not live inside the SSE stream.** The first version awaited `queue.add` inside the
exchange, BullMQ refused the job id (`Custom Id cannot contain :` — a colon is not allowed in a custom
id), and the throw landed *after* the candidate had been sent every frame including `done`, so Nest
tried to write a 500 onto an open `text/event-stream`. ADR-0016 already forbids anything between
`open()` and `close()` from throwing. The enqueue is now after the stream closes, wrapped, and a failure
is logged rather than raised. **The consequence is a phase 4 item**: a lost enqueue means a report that
never arrives, because the stale sweep reads `in_progress` sessions only, so the report route should
queue one when a completed session with answers has none.

**Phase 2 had left `prompt_versions` off the wire.** `answer_evaluations.prompt_versions` is `NOT NULL`
and nothing in `EvaluateAnswerResponse` could fill it. Added, and returned even when the answer could
not be scored — the prompts that failed to get an answer out of the model are exactly the ones somebody
debugging it needs named.

**Two more shapes of the phase-2 Pydantic lesson.** `model_copy(update=...)` skips validation; so does
the **constructor** (`mypy --strict` caught `list[str]` where `list[EvidenceFlag]` was wanted), and
reading a scalar back out needs `.root` or an assertion fails with a message that looks like a logic
bug. Both are in `tasks/lessons.md`.

**The ninth `DROP INDEX questions_embedding_hnsw`,** in a migration that adds one column to a table
Prisma has never heard of. Deleted; `migration-sql.spec.ts` would have failed the build otherwise.

**A second `weak_topics` seam the plan's checklist did not name.** `SelectionInput.weakTopicIds` carried
the same "empty until M4" comment as the bundle's `weak_topics` and wants **ids** where the bundle wants
**names** — the worker has no catalogue, and question selection is weighting a pool it already holds.
One query answers both, which is why `EvaluationsService.weakTopics` returns rows rather than strings.

## What is not done, and is not hidden

- **No route, no screen.** `feedback_ready` is still hardcoded `false` and the completion screen still
  says "Scoring is not built yet". The report exists in `session_reports`; phase 4 serves it.
- **The evaluator has still never run against a real model.** Everything above was proved against a fake
  that returns contract-valid scores and quotes a real substring of the transcript. Phase 7 makes the
  paid run.
- **The flag has no reader.** It is written and logged from here on; phase 6's calibration area draws the
  list, and the agreement metric there has to be able to report with and without flagged answers.
- **A lost enqueue is currently unrecoverable.** See above; it is a phase 4 item in `tasks/todo.md`.
- **`ideal_points` are not yet asserted in `content-no-answer-key.int.spec.ts`** — there is no route for
  the markers to be counted on. The narrower assertions that could be made were:
  `report-assembly.spec.ts` pins the exact five keys of a criterion's candidate feedback, and
  `evaluations.int.spec.ts` checks every `ANSWERKEY-…` marker of the real fixture against the stored
  report.
