# The first paid interview run — what it cost, and what it showed

**2026-09-25, M3 phase 4, branch `feat/m3-interview-engine`.** The owner sat through a full
interview in the browser against `claude-sonnet-5` and reviewed the transcript. This note records
the run and the findings so the next session can diagnose them from the database rather than from
that conversation.

Three corrections to how the run was described afterwards are marked **⚠** below. They matter
because each one would send a reader looking in the wrong place.

### Reading it out of the dev database

```bash
# The transcript, in order, with who spoke and how long each turn took.
docker exec readi-postgres-1 psql -U readi -d readi -c "
select t.seq, t.speaker, t.state, q.position as qpos, t.follow_up_index as probe,
       length(t.text) len, (t.ended_ms - t.started_ms) ms, t.text
from session_turns t
left join interview_session_questions q on q.id = t.session_question_id
where t.session_id = '7ad41245-b13f-412a-8bf3-9250f9ef29dc' order by t.seq;"

# The coverage log, one row per criterion per candidate turn.
docker exec readi-postgres-1 psql -U readi -d readi -c "
select t.seq, jsonb_pretty(t.criteria_covered)
from session_turns t
where t.session_id = '7ad41245-b13f-412a-8bf3-9250f9ef29dc' and t.speaker = 'candidate'
order by t.seq;"

# The pinned snapshot: what the session was actually run against.
docker exec readi-postgres-1 psql -U readi -d readi -c "
select q.position, qq.slug, q.question_version, q.rubric_version,
       jsonb_array_length(coalesce(q.snapshot->'planned_follow_ups','[]'::jsonb)) as probes,
       q.snapshot->>'prompt' as pinned_prompt
from interview_session_questions q join questions qq on qq.id = q.question_id
where q.session_id = '7ad41245-b13f-412a-8bf3-9250f9ef29dc' order by q.position;"
```

**The snapshot is still the one the session ran against**, even though the bank has been re-imported
since (§5). That is the pinning rule doing its job, and it is what keeps this session diagnosable:
`probes_in_snapshot` is `0` for all four questions while the live rows now carry 2 each.

## 3. The owner's findings, as observed

1. **Zero follow-ups in the whole session.** `follow_up_index` is null on every interviewer turn;
   the four questions were asked back to back. Confirmed in the data, cause in §4.
2. **Every opening asked three or four things at once.** Question 1: "Walk me through how that state
   comes about, what you would change, and what you would do about the rows that are already wrong."
   Question 3: what you'd write, who you'd send it to, when, *and* a time you actually did it. This
   is the finding that turned out to matter most — see §4.
3. **Question 1's answer was a code block and nothing else.** No prose account of how the state
   comes about, and nothing about repairing the rows already wrong — two of the three things the
   opening asked. **No probe fired**, so the candidate was never pushed on either.
4. **The intro says something untrue.** `interview_intro.v1.md` includes "there is nothing to look up
   and nobody else is listening". The transcript is stored in `session_turns`, M4 will score it, and
   staff can read it. That is a product-principle problem (privacy by default, and the honest-mentor
   voice), not a wording nit.
5. **The reply in `candidate_questions` was cold and mechanical.** Asked what the session was for, it
   answered "assessment happens separately from me… I'm just the interviewer for this session".
   Accurate — it is told it is not assessing anything (plan decision 5) — but it reads like a form.
6. **The transitions repeat.** "Let's move to the next one", "Let's move on", "Let's move to the last
   question" — three of four openings are the same move.

## 4. Why no follow-up fired: one cause confirmed, one falsified, one new

The two hypotheses raised afterwards were: the phrasing call re-adding asks, or stale pre-retrofit
published rows. The evidence settles both, and turns up a third that neither covers.

### (a) Stale published rows — **confirmed, and already fixed**

Every one of the 105 questions in the dev database had an empty `planned_follow_ups`. The database
had been seeded before the planned-follow-up programme landed (2026-09-23), and the importer had
been **correctly refusing to update those rows because they were published** — ADR-0014 decision 5,
"the seed importer never rewrites published content". Its dry run said so in as many words:
`questions: 73 to update` and then 31 named under *"left alone — published, and candidates are
reading them"*.

So the bundle carried no probes, `machine.probes_to_judge` found nothing in play and skipped the
coverage call, and the log recorded `has_probe: false` / `not_judged` for every criterion — all
exactly as designed, given an empty menu.

Fixed with `pnpm db:seed -- --force`: **225 probes across 104 questions**, the number the M3 plan
states, with statuses unchanged (a transition is not an edit). Verified free on `LLM_PROVIDER=fake`:
against a deliberately thin answer the engine asked two planned probes on question 0 — *"What would
you change?"* then *"And the accounts that are already in that state?"* — stopped at
`max_follow_ups`, and wrote real `not_covered` verdicts against probe indices.

### (b) The phrasing call re-adding asks — **falsified**

The pinned prompt and the spoken turn for question 0, side by side:

> **Pinned:** Support have found accounts where money left one and never arrived in the other. This
> is the code that moves it, in JavaScript — the idea is the same wherever you work. Walk me through
> how that state comes about, what you would change, and what you would do about the rows that are
> already wrong.

> **Spoken:** Let's start with a scenario. Support has found accounts where money left one and never
> arrived in the other, and here's the code that moves it — take a look below. Walk me through how
> that state comes about, what you would change, and what you would do about the rows that are
> already wrong.

The model added a framing sentence and moved the pointer to the snippet. **It added no asks.** The
three-part question is the bank's, not the model's.

### (c) The openings ask what the probes were written to ask — **new, and not fixed by (a)**

`db-half-finished-transfer` now carries exactly two probes:

| criterion | probe | already in the opening? |
|---|---|---|
| 1 | "What would you change?" | yes — *"what you would change"* |
| 2 | "And the accounts that are already in that state?" | yes — *"what you would do about the rows that are already wrong"* |

**Both probes restate the opening.** So even with the bank repaired, a candidate who answers the
opening has by definition covered both probes, the coverage call will say so, and no follow-up will
fire. Re-seeding fixes the empty menu; it does not fix a menu that duplicates the question.

The pilot rule (CLAUDE.md §5) is the opposite of what these questions do: *the opening prompt asks
one thing, the way an interviewer does*, and **exactly one criterion per question goes un-probed**
because the opening asked it. Here the opening asks all three.

`check-bank.mjs` cannot catch this today. It enforces "every criterion is asked for by the prompt
**or** by a probe", which an opening that asks for all of them satisfies perfectly while making
every probe redundant.

**This is a question-bank problem, not an engine problem**, and it is the thing to fix before a
second paid run is worth spending. What it needs:

1. An audit of how widespread it is. Four of four sampled questions have it; start from the openings
   of the published backend set and count the asks in each.
2. A rule in `.claude/skills/question-bank` and a check in `check-bank.mjs` — the natural form is
   "the opening asks for **one** criterion; every other criterion carries a probe", which is the
   pilot rule stated as something a script can test.
3. Rewriting the openings that break it. That is a content change on **published** rows, so it is an
   admin's edit or a `--force` re-import (ADR-0014 decision 7), and it earns a version.

## 6. What a second paid run should be worth

Not until (c) is fixed. As the bank stands, a second run would spend 4–6¢ to watch the coverage call
correctly decide that nothing needs asking — which is the same interview again with an extra call
per answer. The order is: audit the openings, add the check, rewrite what fails it, re-import, prove
the follow-up path on `fake`, **then** pay to hear it in the model's voice.

The other three findings (§3.4–3.6) are prompt changes, and every one of them is a **new version** —
`interview_intro.v2.md`, and a `v2` of the candidate-questions and question prompts if their wording
moves. A released prompt is never edited in place: sessions and eval runs name the version they
spoke (CLAUDE.md "Prompts").
