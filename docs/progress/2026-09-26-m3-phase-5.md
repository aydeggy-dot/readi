## 1. What tracing looks like now

```
POST /interview/advance ─┐
                         ├─ trace  "interview.advance"  user_id, session_id, {action}
POST /cv/parse ──────────┘                │
                                          ├─ generation "interviewer"  system+user → speech, tokens
                                          ├─ generation "coverage"     …
                                          └─ generation "follow_up"    …
```

`apps/ai-worker/readi_worker/tracing/` is the whole of it and **nothing outside it imports the
SDK**. Six files: `mask.py` (pure), `context.py` (two context variables), `tracer.py` (the
`Tracer` seam and `NullTracer`), `langfuse_tracer.py` (the only SDK importer), `factory.py`
(the env check), `llm.py` (the wrapper), `router.py` (`POST /traces/delete`).

### Four decisions worth knowing

**Tracing is a wrapper, not a call site.** `TracedLLMClient` goes on in `main.py` between the
provider client and everything that uses it. CV parsing, the interview engine and M4's evaluator
are traced by construction; there is no "did you trace this one?" review question and no call site
to forget. It changes no behaviour — `LLMError` propagates untouched after the span is marked,
retries stay where they were, and the recording itself is best-effort, because a tracer that can
turn a working call into a failing one is worse than no tracer (there is a `HostileTracer` test
for exactly that).

**A request is a trace; a model call is a generation.** So `ai_call_log.langfuse_trace_id` is the
*same* for an exchange's `coverage` and `follow_up` rows. That is the right grain: they are one
conversation turn and only readable together, and the column says trace, not observation.

**Two context variables carry what the seam cannot** (`tracing/context.py`, which explains itself
at length). The trace id, because it is read where an `AiCallRecord` is built — three files and
six functions away from anything that knows tracing exists, and threading it through would put a
tracing parameter on every function in between. And the call label, because `LLMClient`
deliberately does not know *why* it is being called: "interviewer" and "follow_up" are the same
call to it, and without the label every generation in Langfuse would be named "llm" and the traces
would be unreadable.

**Two opaque uuids now cross to the worker** — `user_id` on `CvParseRequest` and on
`InterviewSessionBundle`. They exist for one reason: a trace has to carry a `user_id` (ADR-0008)
or account erasure cannot find it again. Neither reaches a prompt. `cv.int.spec.ts` pins the exact
field list the worker receives and now names `user_id` with the reason beside it, and
`session-bundle.spec.ts` asserts the same for the bundle. `docs/privacy/subprocessors.md`'s
promise — "never the account's name, email, phone **or id**" — was edited rather than quietly
broken: it now says two opaque uuids cross and why.

### Masking is wider than the ADR asks, on purpose

ADR-0008 requires masking on **CV-parsing** traces. The hook is set on the client, so it runs on
everything, and that is deliberate: a candidate types their own email into a wrap-up answer often
enough, and one rule over everything is a rule that can be read and tested where "masked on this
path and not that one" is a rule nobody can check. It costs a little detail on interview prompts,
which are staff-written and almost never contain a URL.

It removes emails and phone numbers (reusing `logging_config.scrub`, which already mirrors the
API's `scrub.ts`), URLs including bare `linkedin.com/in/…`, and a conservative street-address
pattern. The address regex will miss plenty — addresses are not a regex — and the module says so
rather than implying otherwise. **It may never raise**: a mask that throws inside the SDK's export
path could, at worst, send the unmasked value, so everything is wrapped and an unmaskable value
becomes `[redacted-unmaskable]`.

## 2. Off without keys, and how that is proved

`build_tracer` returns `NullTracer` unless **both** keys are set. The SDK is not constructed, and
because `langfuse_tracer` is imported lazily inside the live branch, it is not even imported — a
worker with no Langfuse configuration does not pay for the OpenTelemetry stack it brings.

`tests/test_tracing.py` (20 tests) holds it:

- the builder is handed a live factory and **the factory is never called** without keys;
- `NullTracer` mints no trace id and both deletions return 0;
- through the real app: an interview exchange's `ai_calls` all carry `langfuse_trace_id: null`;
- `POST /traces/delete` answers `{"enabled": false, "deleted": 0}` — a success, not a failure;
- one key without the other is refused by `Settings` at startup. Half on is a typo, not a
  configuration, and silently disabling it would hide a production misconfiguration until somebody
  went looking for traces that were never sent.

The enabled path is tested with an injected `RecordingTracer`: the generations are named for their
purposes, every call of an exchange carries the one trace id, a CV parse traces under the user
whose CV it is, an unreadable file opens **no** trace (an empty trace is noise in a store we pay to
keep), and a failed call is marked `ERROR` rather than dropped.

What no test can do without an account: prove Langfuse actually deletes anything. That is §4.

## 3. Deletion, and why erasure fails rather than continues

The worker deletes, because it is the only holder of the credentials (ADR-0004).
`POST /traces/delete` takes `{user_id}` (erasure) or `{expired: true}` (the sweep); neither is a
400, because a silent no-op would look like a working sweep for ever.

On the API side, `TracesService`:

- **`deleteForUser` throws** when the worker is unreachable, so `eraseUser` fails and the next
  hourly sweep retries the whole of it. Continuing would erase the user row and strand their
  traces, because the only id that could find them is a tombstone by then. Traces and files now go
  **before** the transaction, in that order, for the same reason files already did. Two new
  integration tests: erasure sends exactly `{user_id, expired: false}`, and an unreachable worker
  leaves the account intact for the retry.
- **`purgeExpired` logs and returns 0** when the worker is down, and runs last in the hourly sweep.
  Nothing downstream waits on it, and throwing would abandon the rest of the sweep.

The worker's delete loop always re-reads **page 1**: deleting shifts the pages under a cursor, so
walking `page=1,2,3…` while deleting skips traces. It stops when a page holds nothing it has not
already deleted, which also terminates cleanly against Langfuse's asynchronous delete. Bounded at
2,000 per call; the hourly sweep drains the rest.

The retention window lives in the **worker** (`LANGFUSE_RETENTION_DAYS`, default 30), not the API:
it is a fact about the store the worker talks to, and putting it on the API side would be a number
to keep in step. Keep it aligned with the recordings retention M5 adds.

## 4. What is left, and it needs keys

`docs/runbooks/langfuse-enable.md` is the ten minutes: create the account **on the EU region**
(the hostname is the region, and regions are separate down to the user account, so a wrong one
means a new account and a migration), paste the pair into `apps/ai-worker/.env`, restart, then
four verifications and two settings in the Langfuse project itself.

Until that is done, the kickoff item **"verify retention and bulk trace deletion" stays open**.
ADR-0008 says it is verified in M3; it cannot be, and pretending otherwise is worse than carrying
it. The code is built, typechecked against the SDK's own types by `mypy --strict` — which is most
of what *can* be verified without an account — and tested against an injected double.

## 5. Dependency

`langfuse==4.15.6`. ADR-0001's maturity rule: the 4.15 line opened 2026-08-27, a month old, and
4.15.6 is its latest patch. It brings 14 transitive packages, almost all OpenTelemetry. It also
installs `httpx` 0.28 alongside the `httpx2` we pin — different distributions, different module
names, no clash.

Justification, since CLAUDE.md asks for one: ADR-0008 already names the SDK's masking hook, and
the alternative is reimplementing OTLP ingestion batching and the trace API by hand against a
service we cannot test against. The SDK also gives `mypy --strict` something to check our calls
against, which is the only verification available before keys exist.
