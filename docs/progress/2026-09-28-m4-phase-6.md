# M4 phase 6 — the calibration tool

**2026-09-28, branch `feat/m4-evaluation`.** `/admin/calibration`: a person marks an answer the model
has already marked, without being shown its marks. Built, tested and demonstrated end to end against
**staff-written answers only** — screenshots in `apps/web/e2e/.artifacts/calibration-*-360.png`.

Nothing was spent. The demonstration runs on `LLM_PROVIDER=fake` like the rest of the e2e suite.

---

## 1. The four rules, and why they live in one file

`apps/api/src/evaluations/calibration.service.ts`. Each of these fails **silently** if it is restated
anywhere else — a bug in the dashboard's arithmetic is visible on the screen, a bug in the consent
filter shows one candidate's interview to a member of staff they told no and looks exactly like
working software.

1. **Nothing is sampled except through a current `transcript_review` grant.** The set comes from
   `ConsentsService.usersGranting`, which is `isCurrentGrant` written once. The integration spec
   holds it in four directions: never granted, granted then withdrawn, granted against an **older
   version** of the wording, and granted by somebody who is not staff while the gate is closed. The
   withdrawal case checks the *read* as well as the list, because a reviewer may be holding a link.
2. **`CALIBRATION_ALLOW_CANDIDATE_TRANSCRIPTS` is off**, and while it is, only answers written by
   staff accounts are offered. That is the owner's "not live until the reviewer agreement is signed"
   held in code rather than in a convention. Consent is still required of staff, so what was
   demonstrated is the real path and not a bypass of it. A test opens the flag and watches the same
   answer appear, so the gate is proved in both positions.
3. **A reviewer is never shown the model's marks**, and never the candidate's name, email or id.
   `CalibrationAnswer` is a **separate shape**, not an `Omit<>` of the evaluation: a field omitted by
   subtraction comes back the first time somebody widens the parent. The test asserts it over the
   **raw JSON**, the way `content-no-answer-key.int.spec.ts` does, because the field that leaks is
   the one nobody remembered to leave out.
4. **Reading an answer is the audited event** — `calibration.answer.read`, one row per read, ids and
   counts only. Not the score: consent was asked for a person *reading* a candidate's words, so that
   is what is recorded, whether or not marks follow. A refused read writes nothing, which is also
   tested.

A reviewer is not offered **their own** answer. They would agree with themselves and the dashboard
would read it as the evaluator being right.

## 2. What is on the screens

- **The queue** (`content_expert`): what is waiting, what this reviewer has already marked, and a
  `flagged` filter. Plain GET form, link pager, no JavaScript — the house pattern.
- **The answer**: the question, the whole exchange with its follow-ups, and the pinned rubric with
  **all five descriptors per criterion as the radio labels**. A reviewer picking a rung should be
  reading that rung's own words; it is also what makes "rung 3 and rung 4 cannot be told apart" a
  thing they can tell us, in the note beside the marks.
- **Flagged evidence**: the answers whose stored quotes matched a phrase that reads like an
  instruction, with the phrase list, commonest first. The list M4 phase 3 said this area would draw.
- **Agreement** (`admin` only): the five figures the `/evals` harness prints, overall and per rubric
  and per question, with rows under five answers marked as too thin to read as a measurement.

**Why the dashboard is an admin's screen and the queue is not.** An aggregate a reviewer reads before
marking is still the model's opinion reaching them first. Aggregate-only for the same reason: a row
naming one answer's marks would undo the blindness for everyone who has not marked it yet.

## 3. Two things that were already there, and one that was not

- **`calibration_scores` already existed** in the schema, from the M4 phase 0 migration, already in
  `TOMBSTONED_COLUMNS` and already handled by erasure. **No migration was needed** and none was
  written. What was missing was everything above the table.
- **The `@@index([status, createdAt])` on `answer_evaluations`** carries the comment "the calibration
  sampler draws recent, scored answers (ADR-0017)" — written in phase 0 for this query.
- **The agreement arithmetic is new, and it is a second implementation of one definition.**
  `calibration-agreement.ts` mirrors `readi_worker/evals/metrics.py`'s `agreement()`, down to the
  direction of `bias` and to treating a correlation with a constant as undefined rather than zero.
  Its unit test uses the **same pairs** `test_evals_metrics.py` uses and asserts the same five
  figures. CLAUDE.md warns that two copies drift; the cost is stated in the file rather than
  discovered later, because a dashboard percentage and a harness percentage have to be readable on
  one axis.

## 4. What the e2e run demonstrates

`apps/web/e2e/calibration.spec.ts`, 360px, ~20 s: a member of staff sits a real interview, grants
transcript review **on the same consent screen a candidate uses**, and a second member of staff marks
the answer. Then the flags list, the dashboard as an admin, and a 404 for a candidate at every URL.

One answer contains a deliberate injection attempt, placed in the **first** answer and first within
it, because the stand-in evaluator quotes the first 90 characters of the candidate's words
(`fake_script.QUOTE_CHARS`) and the flag fires on the **stored evidence**. A phrase further down would
never reach it, and the flagged-evidence screen would have been empty — which looks exactly like a
phrase list that is not wired up. Both `ignore the rubric` and `full marks` fired.

## 5. Two chrome regressions this phase caused and fixed

Adding a third link to the CMS bar broke the header at 360px, twice, and both were found by looking
at the screenshots rather than by a test:

- **The wordmark wrapped**: "Readı" broke across two lines. `shrink-0` — a word that wraps is a
  broken mark.
- **Then the third link was clipped.** The first fix let the nav scroll, which at 360px put `Admin`
  outside the viewport with no affordance at all. A nav may not hide a destination, so the header
  **wraps** instead: crowded, it puts the links on a second row. The candidate header is unaffected —
  it carries at most one staff link below `sm`, so it never overflows.
- **And the dashboard was a table** inside a horizontal scroller, with `Exact` — the figure somebody
  came for — off the right edge. The CMS layout's own note says "nothing here is a table". It is rows
  now.

## What is verified

- `pnpm lint`, `pnpm typecheck` clean. `pnpm test` green: **624** API, **421** worker, 176 web, 119
  shared-types, 56 ui, 3 api-client.
- `pnpm test:e2e calibration` green, five screenshots written.
- `pnpm check:contracts` regenerates cleanly; the OpenAPI drift gate caught a stale document once,
  which is what it is for.
- The new contract is **not** in `contractRegistry`: calibration is TS↔TS and registering it would
  generate Pydantic models the worker never imports.
- `content-no-answer-key.int.spec.ts` is untouched and still passes: `/api/admin/calibration/*`
  matches neither swept prefix, so this route is outside it **by construction** rather than by an
  exclusion list — and it carries the answer key on purpose, because a reviewer cannot mark against a
  rubric they are not shown.

## What is not done, and is the owner's call

- **Going live.** `CALIBRATION_ALLOW_CANDIDATE_TRANSCRIPTS` stays `false` until a reviewed, signed
  `reviewer-agreement.md` exists (ADR-0017 decision 6). Flipping it is the only code change needed,
  and the queue's empty state already says so in words.
- **Nobody has been asked for `transcript_review` yet** in a real deployment, so a production queue
  will be empty and will say `no_consent` until they are.
- **The visual capture does not include these screens.** `E2E_SCREENSHOTS=<label> pnpm test:e2e
  visual` should grow four entries, and the header change is worth a before/after across the whole
  set, since it touches every signed-in page.
- **A reviewer cannot see their own agreement.** The dashboard is admin-only, which is the
  conservative reading of blindness; showing a reviewer aggregates over answers they have *already*
  marked would be safe and is probably what they will ask for first.
