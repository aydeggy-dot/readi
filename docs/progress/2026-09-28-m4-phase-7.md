# M4 phase 7 — measurement, and the things that were only claimed

**2026-09-28, branch `feat/m4-evaluation`.** The last phase of M4: the answer pace measured rather
than guessed, the evaluator's structural fix measured and switched on, the visual review done as a
real before/after, and three latent defects that only showed when the things that had never been
run were run.

Spent: **$3.06** across three paid evaluator runs, all approved and all inside their caps.

---

## 1. `rejected_criteria` is gone, and the schema is the default

Its own handover is `2026-09-28-strict-criteria-run.md`; the short version:

| | answers | calls | rejected | unscored | ¢/answer |
| --- | --: | --: | --: | --: | --: |
| v2 baseline, three opus runs | 180 | 297 | **74 (25%)** | 20 | 4.24 |
| **strict schema, three runs** | 90 | 90 | **0** | 0 | **3.40** |

One call per answer, ninety times; at the baseline rate the chance of that is 6 × 10⁻¹². Sessions
cost **13.6¢ at 15 minutes and 27.2¢ at 30**, down from the 40.3¢ the model decision was taken on.
`EVALUATOR_STRICT_CRITERIA_SCHEMA` now defaults true.

**One finding was raised and then withdrawn, and the withdrawal is the useful part.** After the
second run, strict appeared to read the six `frontend`/`qa` rubrics differently from v2 — 9 points
less agreement with the written expectations, and a fairness drift of +0.17 against v2's −0.06. It
was reported rather than smoothed over, with the one cheap thing that would settle it: a repeat run,
because a noise floor needs two runs of the same configuration and there was only one. The repeat
came back 89%/0.11 against v2 — *better* agreement than either configuration manages with itself —
and a drift of −0.06, v2's figure to the decimal. A difference that reverses when you run it again is
not a difference. **The lesson is that one run per cell cannot tell a change from a wobble**, and the
harness can now measure its own noise floor because `--rubric` makes a repeat cheap.

## 2. The answer pace, measured — `pnpm --filter @readi/api interviews:pace`

`interviews/pace.ts` (pure) + a thin CLI. It reports; the constants stay the owner's.

On the dev database — **4 real sessions, 20 answers, which the report says on its face**:

```
Opening answers      n=12  median  74s  p90 198s  longest 236s
Follow-up answers    n= 8  median  61s  p90 224s  longest 224s
Their own questions  n= 3  median  43s  p90  54s
Interviewer latency  n=33  median 3.7s  p90 6.1s

SECONDS_FOR_A_QUESTION     120s   3 of 12 opening answers ran past it
SECONDS_FOR_A_FOLLOW_UP     45s   5 of 8 follow-up answers ran past it
SECONDS_TO_OPEN_A_QUESTION 165s   DOES NOT COVER a p90 answer plus a p90 probe (422s)
```

**The one thing worth a decision: `SECONDS_FOR_A_FOLLOW_UP` is 45 s and five of eight follow-up
answers took longer**, median 61 s. That is the reserve deciding whether to *ask* a probe, so on this
evidence the engine starts probes the clock cannot finish — the same shape as the problem the
2026-09-27 decision fixed for opening a question. **n = 8**, so it is a shape and not a number, and
the report refuses to let it read as one: under 40 answers it prints NOT ENOUGH TO SET A CONSTANT
FROM and marks every line thin. A reassuring sanity check alongside it: median pace gives 4 questions
per 15 minutes, which is exactly `INTERVIEW_PLANS`.

**Running it found a bug in it**, which is the argument for building the report before needing it.
Three sessions reported answering 5 or 6 questions against a budget of 4 — impossible. Spec §4.3
gives the candidate their own questions at the end and those are candidate turns too, 8 of 51 in that
database; counted as answers they broke the arithmetic visibly and would have dragged the median down
invisibly. Two more traps have tests rather than comments: a session the stand-in drove is excluded
and counted (that database held 47 fake calls beside 42 real ones), and a session with no answers no
longer produces a pace out of the interviewer's latency alone — it was offering several hundred
questions per 45 minutes, a figure that looks like a measurement and is made of nothing.

The three reserves are copied from `budgets.py`, which CLAUDE.md is right to distrust, so the copy is
**checked rather than trusted**: the spec reads that file and fails if they drift.

## 4. Three defects found by running things that had never been run

- **`interview.spec.ts` had a latent flake.** The completion screen asserted `Question 0 for <mark>`,
  but `getByText` matches substrings and every probe reads "Probe one on question 0 for <mark>…", so
  it resolved to three elements and failed strict mode. It passed only while question selection
  happened to leave question 0 unprobed. It asserts the whole prompt now.
- **`measure()` in `slow-network.spec.ts`**, the M3 leftover. It timed `page.goto` with a wall clock,
  which measures our own call rather than the page load and, on a route the Next router had already
  prefetched, measures the swap — the source of the CMS form's *negative* duration and of the
  interview screen reading 1221 ms when nothing else was under 2800. It now leaves for `about:blank`,
  drops the HTTP cache, and reads `PerformanceNavigationTiming.duration` after the load event. A
  navigation served from cache fails the test instead of passing flatteringly.
- **The capture's first attempt photographed the wrong page twice**, and the only tell was two files
  with identical byte counts: the first `/admin/calibration/…` link on the queue is the nav's own link
  to *flags*, so `.first()` never found an answer. An answer id is a uuid, so that is what is matched.

## 5. A trap in the before/after workflow itself, not fixed

`apps/web/tsconfig.json` includes `.next/types/**/*.ts` — the **dev** build's generated route
validator — and the e2e build type-checks against it even though it writes to `.next-e2e`. So the
workflow this spec's own README describes (capture on one commit, switch, capture on the other) fails
on the second capture with errors naming routes that do not exist at that commit:

```
.next/types/validator.ts(53,39): error TS2307: Cannot find module
  '../../src/app/(admin)/admin/calibration/[id]/page.js'
```

`rm -rf apps/web/.next/types apps/web/.next/dev/types` unblocks it, and the directory is a
regenerable cache. **Not fixed**, deliberately: adding `.next-e2e/types` to the include creates the
same failure in the other direction (an e2e run on one branch would then break `next build` on
another), and the honest fixes — a second tsconfig, or dropping the generated types from the
type-check — are each a bigger change than the trap deserves. It is written down in the visual
README, which is where somebody will meet it.

## What M4 leaves open

- **The gold set is empty**, and it is the one thing that would turn every agreement figure in this
  milestone from a regression baseline into evidence about quality. It waits on a signed reviewer
  agreement (ADR-0017) and on pilot candidates consenting.
- **The fairness result is fairness to *model-written* Nigerian English** until real answers exist.
  Anything repeating the figure repeats that clause with it.
- **`SECONDS_FOR_A_FOLLOW_UP`** — see §2. A decision for the owner, on more data than 8 answers.
- **`CALIBRATION_ALLOW_CANDIDATE_TRANSCRIPTS` is still false**, and flipping it is the only code
  change needed once the agreement is signed.
- **Nothing records which output schema scored a stored evaluation.** Fine while the flag never
  moves in production; the day it does, the date stops answering the question.
