# M1 handover — auth, profile, consent, onboarding, CV, export and deletion

**Date:** 2026-09-20 · **Branch:** `feat/m1-auth-onboarding` (rebased onto `main` after M0 merged;
not pushed) · **Status:** done, reviewed, awaiting the owner's end-to-end check and pull request

## What was built

**Phase 1 — API foundation (ADR-0009).** Better Auth 1.7 inside NestJS at `/api/auth/*`, first-party
cookies, a global default-deny guard with `@Public()` and `@Roles()`, email and SMS providers with a
Redis-backed dev mailbox, Resend and Termii for production, rate limits (per IP per route, plus
per-number OTP caps), a trusted client-IP header proven by a shared proxy secret, PII scrubbing in
both runtimes' logs, an audit log, and the `admin:grant` CLI.

**Phase 2 — web auth and onboarding (ADR-0012).** Sign-up and log-in by email, Google and phone OTP;
password reset; the onboarding flow (goals → CV → privacy choices → home); profile and consent
screens; `/admin`; `packages/api-client` generated from the OpenAPI document; sessions resolved on
the server (`requireUser`/`requireOnboarded`/`requireAdmin`), with `proxy.ts` only routing
cookie-less visitors.

**Phase 3 — CV pipeline (ADR-0010).** Browser uploads straight to object storage with a presigned
PUT that signs type and length, a quarantine prefix with a one-day expiry, magic-byte checks on
confirm, a BullMQ job to the Python worker, text extraction (PDF and DOCX), an `LLMClient` adapter
(Anthropic, plus a deterministic fake), a versioned prompt that wraps the CV as data, schema-checked
output normalised in code, cost recorded in `ai_call_log` as micro-USD, and a review/edit screen.

**Phase 4 — export and deletion (ADR-0011).** `GET /api/me/export` returns everything held about the
user as a download, with a 15-minute link to the CV file and no secrets. `POST /api/me/deletion`
takes a typed `DELETE` and a sign-in from the last 15 minutes, then soft-deletes: sessions revoked,
every sign-in method blocked by one Better Auth hook, and an email or SMS telling the user the date.
An hourly sweep erases due accounts — files first, then the row and its cascades — and replaces the
user's id in `audit_logs` and `ai_call_log` with a tombstone. `admin:cancel-deletion` restores an
account during the grace period, audited.

**Phase 5 — end to end.** Playwright drives the real apps at 360px: sign-up → verification email in
the dev mailbox → goals → a real PDF the worker parses with `LLM_PROVIDER=fake` → privacy choices →
home, plus export → delete → refused sign-in. A CI `e2e` job runs it. `docs/privacy/subprocessors.md`
records who processes personal data today, what is wired but off, and what each later milestone adds.

## The M1 review

Five reviewers each took one dimension (authz, validation and contracts, privacy, tests, web). Every
finding was re-verified in the source before anything was changed. Two blockers, both fixed:

1. **Better Auth's phone password-reset routes were live.** `/phone-number/request-password-reset`
   stores a fresh code for any number without sending it anywhere (we never configure a sender), and
   `/phone-number/reset-password` then sets a password — creating a credential account for a
   phone-only user. Guessing the code took over the account. All three unused routes now 404.
2. **Sentry was configured to send request bodies.** `sendDefaultPii: false` does not cover them in
   the JavaScript SDKs. With a DSN set, a 500 during sign-in would have carried the password.

Should-fix items fixed in the same pass: erasure now catches suffixed verification identifiers and
expired codes are purged hourly; a consent decision against superseded wording no longer counts;
CV parse allowances are only spent once the file arrives; the export includes the avatar and warns
when stored CV JSON stops validating; the admin CLIs record who acted; the web app gained error,
not-found and loading boundaries, a session-expiry path on every mutation, wrapping for long
addresses and tags, focus rings and field borders that meet 3:1, feedback when a tag list is full,
a way to enter CV details without a file, and copy that admits sign-in is blocked during the grace
period. Deferred items are listed in `tasks/todo.md`.

## Decisions and deviations

- **Deletion cancellation is an admin action**, not self-service: a soft-deleted account cannot sign
  in, and being signed in is what self-service would need (ADR-0011, alternatives).
- **Erasure is a sweep, not a delayed job**, so the database stays the only record of what is due.
- **The e2e run owns its own database, bucket, ports and build folders**, so it can run beside
  `pnpm dev` and never writes `apps/api/dist` or `apps/web/.next`.
- **`--input` and `--ring` were darkened** to the ADR-0013 values (4.83:1 and 7.56:1) rather than
  waiting for D1: the shadcn defaults are 1.2:1 and 1.5:1, which is a real accessibility failure now.
- **The dev mailbox stays gated on `NODE_ENV` and the console providers** for M1; a staging box left
  on those settings would expose OTPs, so M10 adds an explicit flag.

## Known issues and notes

- The message catalogue ships whole to the browser (~4 KB gzip) because `t()` indexes it
  dynamically; splitting it is an M10 task with a byte budget to keep it split.
- No component tests in `apps/web`; the riskiest logic was pulled into tested helpers instead.
- `SUPPORT_EMAIL` (API) and `NEXT_PUBLIC_SUPPORT_EMAIL` (web) must be set to a real address before
  production — both refuse a `.invalid` placeholder there.
- The owner's dev database holds a leftover walkthrough account, `phase4-check@example.com`.
- Google sign-in has never been exercised against real credentials (no client id configured).
