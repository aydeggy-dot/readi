# M2.5 — Roles, levels and stacks become content

Branch: `feat/m2.5-roles`, cut from `main` at `833e3fa`. Plan written 2026-09-22 and **approved by the
owner the same day**, with the four decisions recorded under "Launch roles" below. Each phase stops for
the owner.

## Context

`frontend | backend | qa` and `intern_junior | mid` are defined once, in
`packages/shared-types/src/constants.ts`, and then copied into four independent closed sets: a Zod enum,
two Postgres enums (plus two enum **array** columns), a generated Pydantic `Literal`, and an i18n
message namespace whose keys *are* the enum values. Adding a role today is a code change in five
languages' worth of artefacts and a database migration.

That is the wrong shape for a product whose growth story is "more roles". It is also about to get
worse: M3 specs `InterviewSession (… role, level …)` and question selection "filtered by role/level",
which would bake a fifth and sixth copy in, and M3 has no stack dimension at all — so a Java/Spring
candidate and a Node candidate would get the same backend questions.

Nothing today models a technology stack beyond `Profile.stack String[]`, an unvalidated free-text tag
list. The one role→stack relationship in the product is `STACK_SUGGESTIONS` in the browser, whose
`backend` entry is already `["Node.js", "Python", "Java", "Go", "PHP", "Laravel", "Django", …]` — the
proposed variants, written as suggestions.

So M2.5 does three things: makes roles, levels and stacks **CMS-managed content** with the M2 workflow;
adds **stack** as a dimension on questions and on the candidate's profile; and writes the **role
catalogue** that says which roles come next and why. Then M3 is built on top of it.

The catalogue draft is already written: **`docs/role-catalogue.md`**.

## Decisions this plan takes

| # | Decision | Why |
|---|---|---|
| 1 | Three new publishable entities: **`CareerRole`**, **`CareerLevel`**, **`Stack`** — full `draft → in_review → published → retired`, `content_versions`, audit, `seed_managed`, review state | Adding a role becomes a content task, exactly as the brief asks. `CareerRole` rather than `Role` because Prisma already has an RBAC `Role` enum |
| 2 | Two join tables: **`CareerRoleLevel`**, **`CareerRoleStack`** | Which levels a role offers, and which stacks belong to it. The `TrackTopic` shape, which the codebase and the CMS already know |
| 3 | **Slugs on the wire, uuids in the database** | `?role=backend` filters, seed files and e2e selectors keep working; `content-query.ts` keeps its allow-list shape. Seed files already refer to everything by slug |
| 4 | **Stack applies to questions and to the profile — not to tracks** | Tracks stay keyed by `(role, level)`. A stack dimension on tracks multiplies the content matrix by six before a single stack track exists; the brief asks for stack-specific *questions*. The door stays open (`tracks.stack_id` is a later migration) |
| 5 | A question with **no stack rows is general to its role**; with stack rows it is offered only to candidates on one of those stacks | The brief's requirement, written as a pure predicate with tests, because M3's selection will depend on it |
| 6 | **Labels come from the API**, and `targetRoles.*` / `levels.*` leave `en.json` | A database-managed role has no message key. Consequence: role labels are not translatable through the i18n catalogue — recorded in the ADR; English only at launch |
| 7 | `CvParseRequest` carries **labels, not keys** (`target_role_label`, `level_label`, `stack_label`) | The worker's `ROLE_LABELS` / `LEVEL_LABELS` maps exist only to turn a key into prompt prose. With roles as data, the API owns the label. Deletes the maps and the test that guards them |
| 8 | `Profile.stack` (free text) is renamed **`technologies`**; the curated variant is `target_stack` | Two fields called "stack" meaning different things is a bug waiting to happen. "What I know" and "which variant I am interviewing for" are different questions |
| 9 | **One migration, with an inline backfill** | There is no production database (M2 handover: "production has no content"), so a three-step expand/contract buys nothing. Local and CI databases are migrated in place |
| 10 | The M3 transport ADR becomes **ADR-0016**; this milestone takes **ADR-0015** | M2.5 lands first |

## Launch roles — the owner's decisions (2026-09-22)

- **Launch content is frontend, backend, QA and full-stack.** Full-stack is near-zero content cost once
  question↔role is many-to-many: existing frontend and backend questions carrying a second role tag,
  plus a handful of boundary questions.
- **Data analyst goes to wave 2**, as argued: it needs a bank written from scratch (M2 spent a phase on
  14 questions for three roles), its rubric dimensions are not a reuse of the engineering ones, and its
  central round is live SQL. The catalogue now records that it **cannot launch until there is a SQL
  practice surface** — the bank alone does not make it honest prep.
- **AI/LLM Engineer moves from wave 3 to wave 2**, ahead of DevOps and Mobile: the best conversational
  fit on the list and almost no prep competition. It still needs its own bank and expert review, so
  **M2.5 writes no content for it** — the move is a catalogue decision only.
- **The wave order stays marked as argued, not measured.** The owner is validating it with bootcamp
  contacts; the catalogue says so in three places rather than one.

So this milestone's content work is unchanged: no new bank, only the seed files for today's roles,
levels and stacks, and full-stack as a tagging exercise once the many-to-many link exists.

## Data model

```
CareerRole    id, slug, name, summary?, position, supported_question_types QuestionType[],
              status, version, seed_managed, created_by_user_id?, published_at?,
              ai_draft_unreviewed, reviewed_by_user_id?, reviewed_at?, timestamps
CareerLevel   id, slug, name, summary?, rank Int, status, version, …same content columns
Stack         id, slug, name, summary?, status, version, …same content columns

CareerRoleLevel  (role_id, level_id, position)     @@id([role_id, level_id])
CareerRoleStack  (role_id, stack_id, position, is_default)   @@id([role_id, stack_id])

QuestionCareerRole  (question_id, role_id)    @@id, index on role_id
QuestionCareerLevel (question_id, level_id)   @@id, index on level_id
QuestionStack       (question_id, stack_id)   @@id, index on stack_id   -- empty = general
```

Changed columns:

| Was | Becomes |
|---|---|
| `Profile.targetRole TargetRole` | `targetRoleId` → `CareerRole` |
| `Profile.level ExperienceLevel` | `targetLevelId` → `CareerLevel` |
| — | `Profile.targetStackId` → `Stack`, nullable |
| `Profile.stack String[]` | `Profile.technologies String[]` (rename only) |
| `Track.role`, `Track.level` | `trackRoleId`, `trackLevelId` FKs; `@@index([roleId, levelId, status])` |
| `Question.roles TargetRole[]`, `levels ExperienceLevel[]` | the three join tables above |
| `enum TargetRole`, `enum ExperienceLevel` | dropped |

The partial unique index `tracks_one_published_per_role_level` keeps its meaning, on the new columns.
**Read the generated migration before applying it** — Prisma proposes dropping hand-written SQL it
cannot see (the M2 lesson: the HNSW index, and now this partial unique index too).

`ContentEntityType` gains `career_role`, `career_level`, `stack`; `TOMBSTONED_COLUMNS` gains their
`created_by_user_id` and `reviewed_by_user_id`; the schema test that proves completeness will say so.

**Retiring is refused while in use.** Retiring a role, level or stack that a published track or question
still references throws `role_in_use` / `level_in_use` / `stack_in_use`. This is the failure the M2
handover recorded for rubrics ("retiring a rubric silently hides every published question that uses
it") — worth not repeating on the entity that would blank the whole catalogue.

## Contracts

`packages/shared-types/src/contracts/catalogue.ts` (new) holds `CareerRole`, `CareerLevel`, `Stack`,
their inputs, list items, candidate shapes and the `CareerRolesResponse` onboarding reads.

Changes elsewhere:
- `profiles.ts` — `TargetRole` / `ExperienceLevel` Zod enums **deleted**; `target_role`, `level` become
  `Slug` (`z.string().regex(SLUG_PATTERN).max(80)`), plus `target_stack: Slug.nullable()`;
  `stack` → `technologies`.
- `content.ts` — `QuestionInput.roles/levels` become slug arrays with new caps
  (`CONTENT_LIMITS.questionRoles: 6`, `questionLevels: 4`, `questionStacks: 8` — today's `.max(3)` and
  `.max(2)` are literally the enum cardinalities); `stacks` added; `ContentListQuery` gains `stack`.
- `seed.ts` — same, plus `SeedCareerRole` / `SeedCareerLevel` / `SeedStack` file shapes.
- `cv.ts` — `target_role`/`level` replaced by `target_role_label`, `level_label`,
  `stack_label: string | null`. **Registered contract**, so `pnpm gen:contracts` regenerates Pydantic.
- `constants.ts` — `TARGET_ROLES` and `EXPERIENCE_LEVELS` **deleted**. This is the module browser code
  imports synchronously, so every consumer switches to server-provided options (below).

Unknown or unpublished slugs become a service-level `ApiError(400, "role_not_found")` rather than a Zod
rejection. The existing negative tests (`target_role: "devops"`) keep their meaning and their 400.

## Where the closed set is read today, and what happens to it

From the audit — every site, grouped by how it breaks.

**Breaks at compile time (good).** `apps/web/src/lib/stack-suggestions.ts` — the only
`Record<TargetRole, …>` in the repo. Deleted: suggestions come from the role's stacks.

**Breaks silently at runtime (the real work).** Nine `` t(`targetRoles.${x}`) `` / `` t(`levels.${x}`) ``
lookups: `(app)/profile/page.tsx:31,33`, `(admin)/admin/content/tracks/page.tsx:54`,
`tracks/[id]/page.tsx:28`, `questions/page.tsx:62`, `onboarding/profile-form.tsx:126,135`,
`admin/question-form.tsx:238,258`, `admin/track-form.tsx:158,169`, `admin/content-list.tsx:110,118-121`.
All replaced by the `name` on the row the API returns.

**Client components that import the constants.** `profile-form.tsx`, `question-form.tsx`,
`track-form.tsx`, `content-list.tsx` — each gets its options as **props from its server page**, which
fetches published roles/levels/stacks. No loading state, no extra round trip, and the lint rule against
value imports of shared-types keeps holding.

**Service filters.** `content.service.ts:618-619` `{ roles: { has: role } }` →
`{ roles: { some: { role: { slug } } } }`; `:1087-1094` `candidatePractice` gains the stack predicate;
`:1105-1120` **`audience()` is the seam** — it already normalises "who is this request for" and grows to
return `{ role, level, stack }`.

**Seed.** `content/seed/roles.yaml`, `levels.yaml`, `stacks.yaml` are new. `questions.yaml` gains an
optional `stacks: [java-spring]`. The loader stays **offline and pure** — it validates slug *syntax*;
the **importer** resolves slugs to rows and raises `SeedReferenceError` for unknown ones, exactly the
pattern `seed-import.ts:501` already uses for topics. Import order gains roles → levels → stacks first.

**Role-as-directory-name.** `review-doc.ts:194` (`inRole` = a path segment) and
`cli/content-review-doc.ts:29-33` (roles = subdirectories) both switch to reading `roles.yaml`, and the
hardcoded `{ frontend: "Frontend", … }` label map at `review-doc.ts:202` is deleted.

**Worker.** `cv/parse.py:39-43` `ROLE_LABELS` / `LEVEL_LABELS` deleted; `cv_parse.v1.md` → **`v2`** with
a stack line ("a backend engineer working in Java/Spring"); `test_labels_cover_every_enum_value`
replaced by a test that the labels are wrapped as data and cannot close the tag.
`tools/compare_cv_parse.py` loses its `choices=[…]`.

**Tests that must change, named now so none is a surprise.** `content-fixtures.ts` (the
`(role, level)` pair-ownership scheme for parallel specs — which this migration *relieves*, since a spec
can now mint its own role row), `giveProfile`, `content-schema.int.spec.ts:43` (the partial-unique-index
test), `cv.int.spec.ts:128-131` (**asserts the exact key set sent to the worker**), `onboarding.int.spec.ts:106`,
`profiles.test.ts:26`, `seed-loader.spec.ts:111`, and the e2e specs that check a radio labelled
"Backend engineer" — which keep working as long as the seeded role is labelled exactly that.

## Phases

Each phase stops for the owner. Ordered so the next phase's work is reviewable against real data.

**Phase 1 — the catalogue exists, beside the enums.**
`catalogue.ts` contracts; the three entities, two join tables, migration; `ContentService` CRUD,
transitions, versions, audit, `retire`-in-use refusal; admin + candidate read endpoints; the three seed
files covering today's roles, levels and the stacks from `STACK_SUGGESTIONS`; the importer creating them
first. **Nothing else changes and nothing breaks** — the enums are still in charge.

**Phase 2 — the CMS for them.**
`/admin/content/roles`, `/levels`, `/stacks`: lists with the no-JavaScript filter bar, create/edit forms,
transitions, version history; a role page that manages its levels and its stacks (the `module-panel.tsx`
shape). The owner can read, edit and publish the catalogue before anything depends on it — the M2 lesson
about building the CMS against real content, applied to itself.

**Phase 3 — the switch.**
Tracks, questions and profiles move onto the catalogue; the join tables replace the enum arrays; the
contracts change from enum to slug; filters, mappers, seed importer, review-doc, the CMS forms, the
onboarding form, `content-query.ts` and the e2e specs all follow; the two Postgres enums are dropped.
The single biggest phase, and deliberately atomic: an enum cannot be half-dropped.

**Phase 4 — the stack dimension.**
`QuestionStack`; `Profile.targetStackId`; `Profile.stack` → `technologies`; the eligibility predicate
(general OR matching stack) as a pure, tested function; the onboarding stack picker with suggestions from
the role; `stacks:` tags on the seeded backend and QA banks; `CvParseRequest` labels and prompt v2.

**Phase 5 — verification and docs.**
ADR-0015; `docs/role-catalogue.md` re-checked against what was actually built (its wave decisions are
already recorded, but "Beyond M3" and the stack lists should match the shipped catalogue); `PRODUCT_SPEC.md` §3, §4.2,
§6.1; `CLAUDE.md` §2 and §5; `content/seed/README.md` and `REVIEW.md`; `docs/PROMPTS.md` (M3's prompt,
and a new M2.5 entry); e2e, screenshots, Slow 4G; the handover and the lessons.

## Verification

```bash
pnpm lint && pnpm typecheck && pnpm check:contracts
pnpm test && pnpm test:e2e
pnpm db:seed && pnpm db:seed          # still idempotent: second run changes nothing
pnpm --filter @readi/api content:review-doc   # regenerates without the directory convention
E2E_SCREENSHOTS=m2.5 pnpm test:e2e visual
```

Proven by hand once and recorded: **add a fourth role end to end through the CMS** — create
"Full-stack engineer", give it levels and stacks, publish it, tag two existing questions with it, and
see it appear in onboarding and in the practice feed **without a code change or a migration**. That is
the whole point of the milestone, and it is the acceptance criterion.

## Risks

- **Phase 3 is large and atomic.** Mitigated by phases 1 and 2 landing the entities and their CMS first,
  so phase 3 is a swap rather than a build.
- **Prisma will propose dropping the hand-written partial unique index** (and the HNSW index) in a
  migration that touches `tracks` or `questions`. Read every generated migration; this exact class of
  bug cost time in M2 phase 5.
- **Losing compile-time narrowing.** `openapi-typescript` currently generates
  `"frontend" | "backend" | "qa"` and the web app leans on it in four files. After the switch those
  become `string`, so the runtime 400 is the only guard — which is why unknown slugs must produce a
  clear, mapped error code rather than a generic failure.
- **`en.json` loses `targetRoles` and `levels`.** Any missed lookup throws at runtime (the i18n helper
  throws on a missing key), so a grep for `` t(` `` with an interpolated key is part of phase 3's
  checklist.

# What the saved M3 plan must change

`docs/plans/m3-interview-engine.md` was written against the enums. Once M2.5 lands, these are the edits —
nothing else in it changes.

1. **ADR number.** The transport/streaming ADR becomes **ADR-0016**; M2.5 takes 0015.
2. **`InterviewSession`** carries `career_role_id`, `career_level_id` and `stack_id?` FKs instead of
   `role TargetRole` / `level ExperienceLevel`. Contracts carry slugs.
3. **Version pinning grows.** Roles, levels and stacks are now versioned content, so the session pins
   `role_version`, `level_version` and `stack_version` alongside the question and rubric versions, and
   the snapshot records the role and stack the questions were chosen for. The pinning test extends to
   "rename the role after the session; the report still says what it said".
4. **Question selection gains the stack rule.** Eligibility becomes: published, rubric published, role
   matches, level matches, **and (no stack tags OR a stack tag matching the session's stack)**. The pure
   predicate written in M2.5 phase 4 is reused rather than rewritten. Weak-topic weighting is unchanged.
5. **The session setup screen reads the catalogue.** Role, level and stack come from
   `GET /api/content/career-roles` (published only), defaulting to the profile's `target_role`,
   `target_level` and `target_stack`. No `TARGET_ROLES` import — it will not exist.
6. **Interview types are per role.** `CareerRole.supported_question_types` decides which types the setup
   screen offers, and what a diagnostic for that role mixes. The plan's "preset 15-minute mixed session"
   becomes "preset mixed session, per the role's supported types".
7. **The session bundle sends labels**, not keys, to the worker — the CV contract already works that way
   after M2.5 phase 4, so the interview prompts use the same shape ("a backend engineer working in
   Java/Spring, at mid level").
8. **Test fixtures get easier.** The `(role, level)` pair-ownership scheme in `content-fixtures.ts`
   exists because the enum had six pairs and four were taken; interview specs can mint their own role
   row instead of claiming a pair. Worth using rather than extending the old scheme.
9. **The question-bank arithmetic changes.** The plan's "8 frontend / 5 backend / 5 QA" gains a
   full-stack role sharing the frontend and backend banks. The 15-and-30-minute decision still holds —
   and gets a little more headroom for full-stack.
10. **`interviews.ts` contracts** reference `Slug` types from the catalogue contract rather than
    `TargetRole` / `ExperienceLevel`.
