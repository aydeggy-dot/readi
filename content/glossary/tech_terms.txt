# Technical vocabulary for speech recognition (M5, ADR-0020).
#
# This file does two jobs, and it is one file so that they cannot drift apart:
#
#   1. It is loaded as **custom vocabulary** (keyterms / word boost) for the speech-to-text
#      provider, so that a candidate saying "idempotent" is not transcribed as "I don't potent".
#   2. It is the **tech-term subset** the accent benchmark scores separately
#      (`/evals/stt_benchmark`). A provider that mishears the vocabulary of the job is unusable for
#      this product however good its overall word error rate looks — and one cannot be tuned for the
#      test without also being tuned for the product, because the list is the same.
#
# Rules for editing:
#   - One term per line. Blank lines and `#` comments are ignored. Case is preserved as written,
#     because it is what a report prints; matching is case-insensitive.
#   - Terms are drawn from what **our own questions actually say** (`content/seed/*`) and from the
#     stacks the catalogue offers (`content/seed/stacks.yaml`). It is not a list of every technology
#     that exists: every provider caps how many keyterms it will take, and a list padded with words
#     no candidate will say makes the cap bite where it matters.
#   - **The order is the priority order.** Every provider caps how many keyterms it will accept, and
#     the loader keeps the first N of this file when it must — so the opening section is the terms
#     most likely to be misheard, and the sections after it run from the vocabulary our banks use
#     most to the vocabulary they use least. Moving a line up is a decision about what a candidate
#     can afford to have misheard.
#   - Prefer the spoken form. A candidate says "Postgres" more often than "PostgreSQL", and both are
#     here; nobody says "k8s" out loud as letters, so "Kubernetes" carries the weight.
#   - Add a term when a bank starts using it, in the same change as the question.
