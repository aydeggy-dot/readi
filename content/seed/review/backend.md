### 1. api-error-shape

**technical** · difficulty 3/5 · roles: backend, fullstack · mid · topic: API design (error handling)

**The interviewer asks**

> You are designing the error responses for an API that a mobile app and a web app both use. What does an error look like, and how does the client know what to do with it?

**What a strong answer covers** — the answer key; never shown to a candidate

- A stable machine-readable code per error, separate from the human message.
- Status codes used by category, including the difference between 401, 403 and 404.
- Validation failures name the offending fields so the client can mark them.
- Nothing internal in the body — no stack traces, no SQL — and a request id for support.
- One shape, the same across every endpoint, written down.

**Rubric: Designing an error contract** (`api-error-contract`)

**Gives clients something to branch on — 40%**

A stable code per error, separate from the human-readable message.

- **0 (absent):** Returns a message only.
- **1 (weak):** Returns a message and expects clients to match on its text.
- **2 (partial):** Has codes, but they are inconsistent or duplicated by the status code alone.
- **3 (solid):** A stable code per error, plus a message for humans.
- **4 (excellent):** As 3, and versions or documents the codes so a client can rely on them.

**Uses status codes honestly — 35%**

The right category, and 4xx versus 5xx placed by whose fault it is.

- **0 (absent):** Everything is a 200, or everything is a 500.
- **1 (weak):** Uses 400 and 500 only.
- **2 (partial):** Mostly right, with one clear misuse (e.g. 404 for a failed validation).
- **3 (solid):** Correct categories, including the distinction between 401, 403 and 404.
- **4 (excellent):** As 3, and can justify a harder case — 409 versus 422, or 429 with a retry hint.

**Says enough, and no more — 25%**

Field-level detail for validation; no stack traces, SQL or internal identifiers.

- **0 (absent):** Either says nothing useful or returns the raw exception.
- **1 (weak):** A generic message for every failure.
- **2 (partial):** Some detail, but leaks something internal.
- **3 (solid):** Field-level validation detail and no internals.
- **4 (excellent):** As 3, and returns a request id so support can find the log entry.

> **The drafter is unsure about:** Marked mid rather than junior because the interesting part is the contract, not the syntax. Is 409 versus 422 (in the top descriptor of criterion 2) a reasonable thing to expect, or is it the kind of distinction that only reads as knowledge because it is obscure?

### 2. n-plus-one-diagnosis

**technical** · difficulty 3/5 · roles: backend, fullstack · mid · topic: Databases and data modelling (query performance)

**The interviewer asks**

> An endpoint that returns 20 records takes 3 seconds in production and 80 milliseconds on your machine. Nothing in the code looks expensive. How do you find out what is happening?

**What a strong answer covers** — the answer key; never shown to a candidate

- Look at the queries the request actually made, not just the code.
- Twenty-one queries instead of one is the signature of an N+1.
- Round trips dominate when the database is across a network, which is why the laptop lies.
- `EXPLAIN ANALYZE` the worst query; check for a sequential scan and the real row count.
- Fetch related rows in one query, or add the index the plan asks for — then re-measure.

**Rubric: Diagnosing a slow query path** (`query-performance-diagnosis`)

**Looks at what actually ran — 40%**

Inspects the queries and their plans rather than reasoning from the code alone.

- **0 (absent):** Guesses at a cause and starts changing code.
- **1 (weak):** Reads the application code only.
- **2 (partial):** Logs the queries but does not read a plan.
- **3 (solid):** Finds the queries and reads an execution plan for the worst one.
- **4 (excellent):** As 3, and measures under a realistic data volume rather than a development dataset.

**Recognises the pattern — 35%**

Names the N+1, or whatever the real shape of the problem is.

- **0 (absent):** No diagnosis.
- **1 (weak):** "The database is slow."
- **2 (partial):** Suspects the right area without naming the pattern.
- **3 (solid):** Identifies the N+1 (or the missing index) and explains why it costs what it does.
- **4 (excellent):** As 3, and distinguishes round-trip cost from row-scanning cost.

**Fixes it without creating the next problem — 25%**

A fix proportionate to the cause, aware of what it costs elsewhere.

- **0 (absent):** No fix, or caching over the top of it.
- **1 (weak):** Adds indexes broadly.
- **2 (partial):** Fixes this query in a way that will not generalise.
- **3 (solid):** Fetches the related rows in one query, or adds the index the plan calls for.
- **4 (excellent):** As 3, and notes the cost — write amplification from indexes, or over-fetching from a join.

> **The drafter is unsure about:** The "fast locally, slow in production" framing is meant to push towards round trips rather than raw query time. It may be too strong a hint. Would you rather the question said nothing about the local machine?

### 3. incident-you-contributed-to

**behavioral** · difficulty 3/5 · roles: backend, frontend, qa, fullstack · mid · topic: Working with a team (incidents)

**The interviewer asks**

> Tell me about a production problem you had a hand in causing. What happened, what did you do at the time, and what changed afterwards?

**What a strong answer covers** — the answer key; never shown to a candidate

- A specific incident, with their own part in it stated plainly.
- What they did during it — and whether they told anyone early.
- How it was resolved, including what was rolled back or hot-fixed.
- A change that outlived the incident: a test, an alert, a check in the deploy.
- No blaming of a colleague or of "the process" without owning their share.

**Rubric: Behavioural answer quality** (`behavioural-answer-quality`)

**A specific, real situation — 30%**

The answer is about one thing that actually happened, with concrete detail — the task, the system, when, who else if anyone — rather than a general description of how the candidate likes to work.

- **0 (absent):** No situation given; answers in generalities ("I always communicate early").
- **1 (weak):** Nothing that fixes it in time or place — a situation named with no detail, or a confident account that turns out to be how they usually work rather than one occasion.
- **2 (partial):** One situation with some context; the task or the timeframe is missing.
- **3 (solid):** One situation, with the context an outsider needs in order to follow it.
- **4 (excellent):** As 3, and says what made it hard — the constraint, the deadline, the thing that was unknown.

**Their own actions — 40%**

What the candidate personally did, in enough detail to judge. Collective phrasing is not a fault; an answer with no recoverable action is.

- **0 (absent):** No action is attributable to the candidate, even after the interviewer asks which part was theirs.
- **1 (weak):** Nothing in the answer is theirs to point at — generic actions ("I fixed it"), or a detailed account of what the team decided with their own part left out.
- **2 (partial):** Some of their own actions, but the sequence or the reasoning is missing.
- **3 (solid):** What they did and why it is recoverable from the answer.
- **4 (excellent):** As 3, including a decision they weighed and what they gave up by taking it.

**Outcome and what they took from it — 30%**

How it ended, including if it went badly, and something specific they do differently now as a result.

- **0 (absent):** No outcome, or an outcome that does not follow from the actions described.
- **1 (weak):** States that it worked out, with nothing to show for it.
- **2 (partial):** An outcome, but the lesson is a platitude ("communication is important") — however specifically the outcome itself is told.
- **3 (solid):** The outcome and one specific thing they changed afterwards are both stated.
- **4 (excellent):** As 3, and the change is one an interviewer could check against how they now work.

> **The drafter is unsure about:** Candidates often arrive coached to avoid admitting fault, so the answers may be evasive regardless of the person. Is this worth asking at mid level, or does it mostly measure interview training? If it stays, should the rubric explicitly reward admitting a mistake?

## Track: Backend engineer — mid-level

`backend-mid` · backend · mid

A starting skeleton for the backend programme: the contract a service offers its clients, and the queries it really makes.

**Topics covered** (core topics drive the readiness score): API design **(core)**, Databases and data modelling **(core)**, Reliability and failure handling **(core)**, Working with a team

### APIs that behave

What a client can rely on, and what it does when things go wrong.

#### Error responses a client can act on

`error-responses-clients-can-use` · 10 min

An error response has two audiences: the developer reading logs, and the code that has
to decide what to do next. A message alone serves only the first.

Give every error a **stable machine-readable code** — `card_declined`,
`rate_limited` — that the client can branch on, and keep the human message for people.
A client that has to match on English text will break the first time the wording
improves.

Use the **status code for the category**: 400 for a malformed request, 401 for "who are
you", 403 for "not yours", 404 for "not here", 409 for a conflict with current state,
422 for a well-formed request that cannot be satisfied, 429 for rate limits, 5xx for
"our fault". A 200 with `{"error": …}` inside makes every caller write special code.

For validation failures, say **which field** and why, as a list — clients want to put
the message next to the input.

Never leak internals. A stack trace or an SQL fragment in a response is both an
operational tell and a security problem; log it with a request id and return the id.

Finally, write the error shape down once and keep it the same everywhere. A client
written against one endpoint should already know how the next one reports failure.

#### The query your ORM actually runs

`the-query-your-orm-runs` · 12 min

An ORM hides the database until it surprises you. The habit worth building is to look
at the SQL it produced before deciding a page is "just slow".

The classic surprise is the **N+1**: one query for a list, then one more per row as
something lazily loads. Twenty jobs become twenty-one round trips, each cheap on your
laptop and expensive across a network. Every ORM has a way to fetch the related rows in
one go (`include`, `join`, `select_related`, `preload`); learn the one you use.

Read the **execution plan** rather than guessing. `EXPLAIN ANALYZE` tells you whether a
query used an index, how many rows it really touched, and how much time went where. A
sequential scan on a large table in a hot path is the usual finding.

Index what you filter, join and sort by — and remember that an index makes reads faster
and writes slower, so they are not free. Composite indexes work left to right: an index
on `(user_id, created_at)` helps a query filtering by `user_id`, but one on
`(created_at, user_id)` does not.

Two more habits: keep transactions short, because a transaction held open while calling
another service holds a connection the pool needs; and never build SQL by string
concatenation — parameters exist so that a name with an apostrophe is not an incident.
