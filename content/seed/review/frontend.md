### 1. js-async-ordering

**technical** · difficulty 3/5 · roles: frontend, fullstack · mid · topic: JavaScript fundamentals (the main thread)

**The interviewer asks**

> A tester says that when they tap Save on their phone the screen goes dead for about two seconds — nothing on it changes at all — and then the "Saved" message appears. They expected to see "Saving…" while they waited. Why does that line never show up?

**Setup the candidate is given**

> ```js
> saveButton.addEventListener("click", () => {
>   status.textContent = "Saving…";
>
>   // Builds the report from about 40,000 rows. Takes ~2 seconds on a mid-range phone.
>   const report = buildReport(rows);
>
>   status.textContent = `Saved — ${report.length} lines`;
> });
> ```

**What a strong answer covers** — the answer key; never shown to a candidate

- The first line did run; the text was set and the browser never got the chance to paint it.
- Rendering happens on the same thread as the handler, and only once the handler has returned.
- By the time a frame could be drawn, `textContent` already said "Saved", so "Saving…" was never on screen.
- Nothing else works during those two seconds either — taps and scrolling wait behind the loop.
- Let the browser paint before the work starts, or move the work off the main thread.
- Check it on a mid-range phone or with the CPU throttled, not on the laptop it was written on.

**Rubric: Understanding what the main thread is doing** (`async-ordering-understanding`)

**Says why the first message never reaches the screen — 25%**

Not that it was overwritten too quickly to see — that no frame was painted between the two assignments, so there was never anything to see.

- **0 (absent):** Concludes the line did not run, or that the code is wrong.
- **1 (weak):** A story about the writes rather than about painting — too quick to see, the second line overwriting the first, the two assignments batched together so only the last survived.
- **2 (partial):** Says the screen did not update, without saying why the update never reached it.
- **3 (solid):** Says the text was set but the browser never painted between the two assignments.
- **4 (excellent):** As 3, and says what was on screen for those two seconds instead — whatever the tap found there.

_Asked for by the opening prompt; no planned follow-up._

**Explains what the browser is doing for those two seconds — 45%**

One thread runs the handler and draws the page and cannot do both at once, so the frame comes after the handler returns.

- **0 (absent):** Treats drawing the page as something that happens independently of the code.
- **1 (weak):** A mechanism that is not this one — the browser batching updates for performance, rendering on another thread, `textContent` being asynchronous.
- **2 (partial):** Says the thread is busy, without connecting that to when the page can be drawn.
- **3 (solid):** Says the same thread runs the handler and paints, so no frame can be produced until the handler returns.
- **4 (excellent):** As 3, and extends it to the rest of the page — the tap that goes unanswered, the scroll that stalls — because they wanted the same thread.

_Planned follow-up — asked only if the answer has not already covered this:_

> Two seconds is a long time — what is the phone actually busy with?

**Gets the work out of the way — 30%**

What they would change, and how they would know it had worked.

- **0 (absent):** No change proposed, or only a message put somewhere else on the page.
- **1 (weak):** A change that leaves no room for a frame — a promise wrapped round the same work, a faster loop, a spinner beside the text, or forcing a synchronous layout after the assignment to push it out.
- **2 (partial):** Names an approach — yield, a worker, do it on the server — without saying what it changes about the two seconds.
- **3 (solid):** Lets the browser paint before the work starts, or moves the work off the main thread, and says why that is what fixes it.
- **4 (excellent):** As 3, and says how they would check — a throttled profile, or a real mid-range phone — and what their choice costs against the other one.

_Planned follow-ups — asked only if the answer has not already covered this, and the second only if the first did not draw it out:_

> What would you change so the tester sees that message?

> How would you know the change had worked?

> **The drafter is unsure about:** **The snippet changed on 2026-09-22 and the question is now mid only** (owner's decision). It used to be four `console.log`s and a zero-delay `setTimeout` — the snippet in every "top ten JavaScript interview questions" video, which sorted candidates by how much interview prep they had watched rather than by what they understood, and three of the four critique passes wanted it changed or cut. It asks the same thing about the main thread from a symptom nobody can have memorised, and the follow-up ("so where does the work go?") is a real one. What I would like checked is whether the fix is still reachable at mid: "let it paint first" is easy to say and fiddly to do, so the rubric puts the mechanism at level 3 and the yielding at level 4, and a candidate who only says "move it to a worker" still scores 3.
> Criterion 3 scores two things at 30% — the change, and knowing it worked — so it carries two follow-ups, the second only reached if the first has not already drawn it out.

### 2. js-loop-that-returns-nothing

**technical** · difficulty 2/5 · roles: frontend, fullstack · intern-junior · topic: JavaScript fundamentals (array methods and return values)

**The interviewer asks**

> This function is meant to give back the jobs that are still open, and whoever calls it gets `undefined` every time. Where is that `undefined` coming from?

**Setup the candidate is given**

> ```js
> function openJobs(jobs) {
>   jobs.forEach((job) => {
>     if (job.isOpen) {
>       return job;
>     }
>   });
> }
> ```

**What a strong answer covers** — the answer key; never shown to a candidate

- `openJobs` has no `return` of its own, so it gives back `undefined` whatever the loop does.
- The `return` inside belongs to the arrow function and ends that call, not the outer one.
- `forEach` throws away whatever its callback returns; it is there for side effects.
- `filter` keeps the items that pass a test and gives back a new array, leaving the original alone.
- `find` is the one to reach for if only the first match is wanted — a different question.

**Rubric: Reading what a loop actually gives back** (`array-return-diagnosis`)

**Says where the `undefined` comes from — 40%**

The outer function never returns anything; the `return` inside belongs to the callback.

- **0 (absent):** Sees nothing wrong, or blames the data.
- **1 (weak):** Puts the fault somewhere it is not — the `if`, the property name, an empty array — whether guessed at or worked through.
- **2 (partial):** Notices that `openJobs` returns nothing, without saying what the inner `return` does instead — or gives that `return` a behaviour it does not have and makes the missing assignment the whole of the bug.
- **3 (solid):** Says the `return` ends the arrow function and the outer one falls off the end, so the caller gets `undefined`.
- **4 (excellent):** As 3, and says the loop itself runs correctly — nothing is broken except what is done with the result.

_Asked for by the opening prompt; no planned follow-up._

**Knows what `forEach` is for — 30%**

That it throws away whatever the callback returns, so no `return` inside it can produce a value.

- **0 (absent):** Treats `forEach` as interchangeable with any other loop.
- **1 (weak):** Gives `forEach` a behaviour it does not have — that the `return` skips to the next item and is otherwise fine, that it stops the loop, that it collects what is returned.
- **2 (partial):** Says `forEach` "does not return anything" without connecting that to the callback's value.
- **3 (solid):** Says `forEach` ignores what the callback gives back, and is there for side effects.
- **4 (excellent):** As 3, and separates it from the methods whose whole purpose is the value the callback returns.

_Planned follow-up — asked only if the answer has not already covered this:_

> Where does the value from that inner `return` end up?

**Writes it the way that says what it means — 30%**

`filter` for every match, `find` for the first — chosen, rather than the first thing that works.

- **0 (absent):** No working alternative.
- **1 (weak):** A change that does not fix it — moving the inner `return` elsewhere in the callback, or capturing what `jobs.forEach(...)` gives back, which is `undefined`. A correct method named in passing is not the fix they proposed.
- **2 (partial):** Gets a correct result the long way — a variable, a loop and a `push` — or names `filter` without being able to say what it gives back.
- **3 (solid):** Uses `filter`, and says it gives back a new array of the items that passed.
- **4 (excellent):** As 3, and says what they would use if only the first open job were wanted, and why that is a different question.

_Planned follow-up — asked only if the answer has not already covered this:_

> How would you write it instead?

> **The drafter is unsure about:** New on 2026-09-22, because `js-async-ordering` became mid only and `javascript-fundamentals` would otherwise have had one general question at intern-junior instead of the floor of two. It is the cheapest question in the bank and deliberately so: the topic needed something a self-taught junior meets in their own code rather than in a video. The risk runs the other way — is it too easy to be worth one of the six questions an hour holds, or does the "which function is this `return` in" part carry it? The follow-up I have in mind is "and if you only wanted the first one?", which is where `find` comes in.

### 3. fetch-failure-states

**technical** · difficulty 2/5 · roles: frontend, fullstack · intern-junior · topic: HTTP, APIs and the network (error handling)

**The interviewer asks**

> You are building a screen that loads a list of jobs from an API and shows them. Besides the jobs arriving, what else does that screen have to be able to show?

**What a strong answer covers** — the answer key; never shown to a candidate

- Four states, not one: loading, empty, error, and data.
- An empty list is a normal result and needs its own message, not an error.
- `fetch` resolves for a 404 or a 500: the status has to be checked, e.g. `response.ok`.
- A request needs a deadline, because a phone that has lost signal hangs rather than failing.
- The error state should offer the user something to do — retry, or go back.

**Rubric: Handling a network that fails** (`network-failure-handling`)

**Covers the states a screen needs — 35%**

Loading, empty, error and data — with empty treated as normal, not as an error.

- **0 (absent):** Only the success case.
- **1 (weak):** Success and a spinner.
- **2 (partial):** Three of the four states, or all four with empty and error run together — whether they are merged by omission or an empty list is argued to be an error.
- **3 (solid):** All four states, with empty and error clearly different.
- **4 (excellent):** All four, plus what the user can do from the error state (retry, go back, contact support).

_Asked for by the opening prompt; no planned follow-up._

**Handles HTTP errors correctly — 40%**

Knows that `fetch` resolves for a 404 or a 500 and that the status must be checked — the single most common mistake in this area.

- **0 (absent):** No error handling at all.
- **1 (weak):** Relies on the request rejecting — a `try`/`catch` only, or the claim that `fetch` throws on a 404 or a 500.
- **2 (partial):** Checks the status, but treats every failure the same way.
- **3 (solid):** Checks `response.ok`, and separates "the request failed" from "the server said no".
- **4 (excellent):** As 3, and distinguishes statuses that deserve different handling (401 vs 404 vs 500).

_Planned follow-up — asked only if the answer has not already covered this:_

> The server answers with a 500 — walk me through what happens in your code from there.

**Thinks about a bad connection — 25%**

Timeouts, a request that never returns, retries, and what is safe to retry.

- **0 (absent):** Assumes the request either succeeds or fails promptly.
- **1 (weak):** Mentions slow networks with no mechanism — or names one the platform does not have, such as a timeout `fetch` applies on its own.
- **2 (partial):** Suggests a timeout or a retry, without saying how or when.
- **3 (solid):** Gives the request a deadline (e.g. `AbortController`) and retries deliberately.
- **4 (excellent):** As 3, and notes that retrying a non-idempotent request can repeat a side effect.

_Planned follow-up — asked only if the answer has not already covered this:_

> Their signal drops halfway through and the request never comes back — what then?

> **The drafter is unsure about:** This is deliberately open rather than a puzzle, so a candidate who has built a real screen does well and one who has memorised trivia does not. The risk is that it rewards talkers. Does the rubric weight (40% on HTTP error handling) put enough of the score on the one thing that is objectively right or wrong? The prompt now says "what the code actually has to check", because without it the wording pointed candidates at spinners and empty states and then scored them on `response.ok`. A reviewer also suggested this would be stronger as a code review — a happy-path component with the missing status check in it — which would make that 40% something the candidate finds rather than recalls. Worth doing? The 500 follow-up is deliberately open so that it does not hand over that `fetch` resolves — is it too open to score criterion 2 cleanly?

### 4. react-state-placement

**The interviewer asks**

> Two components on the same page need to know which job the user has selected: a list on the left and a detail panel on the right. Where would you keep that selection, and why there?

**What a strong answer covers** — the answer key; never shown to a candidate

- Lift it to the nearest component that contains both — not to a global store by reflex.
- Keep the id, not a copy of the job object, so there is one source of truth.
- The job data itself is server state and belongs in a cache that can refetch, not in `useState`.
- Consider the URL, so the selection survives a reload and can be shared.
- Name the cost of the choice — prop drilling, or re-rendering the list when the selection changes.

**Rubric: Deciding where state lives** (`state-placement-reasoning`)

**Chooses a defensible home for the state — 40%**

Local, lifted to the nearest common parent, in the URL, or in a server cache — and why.

- **0 (absent):** No decision, or "put it in a global store" with no reasoning.
- **1 (weak):** Picks a place but cannot say why that one.
- **2 (partial):** Lifts higher than necessary, or reaches for a global store first — including a case for the store built on a claim about re-renders that this tree does not support.
- **3 (solid):** Lifts to the nearest component that needs it, and says why there.
- **4 (excellent):** As 3, and recognises the kind of state it is (server data, UI state, or a URL concern).

_Asked for by the opening prompt; no planned follow-up._

**Avoids duplicating the same fact — 30%**

Derives what can be derived; does not keep two copies that have to be kept in step.

- **0 (absent):** Copies the same value into several places — without noticing, or defending it as an optimisation.
- **1 (weak):** Keeps both copies and proposes keeping them in step — passing the title down as well and updating it alongside the id.
- **2 (partial):** Avoids duplication in the example but cannot generalise the rule.
- **3 (solid):** States the rule — one source of truth, derive the rest during render.
- **4 (excellent):** As 3, with an example of what goes wrong when it is broken (values drifting apart).

_Planned follow-up — asked only if the answer has not already covered this:_

> The detail panel also needs the selected job's title — where does it get that from?

**Names the cost of the choice — 30%**

Prop drilling, re-renders, a store that outlives the screen — no choice is free.

- **0 (absent):** Presents the choice as obviously correct with no trade-off.
- **1 (weak):** Acknowledges a trade-off and names the wrong one — an extra file, some boilerplate — rather than what this choice actually costs.
- **2 (partial):** Names one cost in passing.
- **3 (solid):** Names the real cost of their choice and when it would push them to a different one.
- **4 (excellent):** As 3, and gives the signal they would watch for to change the decision later.

_Planned follow-up — asked only if the answer has not already covered this:_

> Six months from now, what about that decision is most likely to annoy whoever is working on this page?

### 5. react-unnecessary-effect

**technical** · difficulty 3/5 · roles: frontend, fullstack · intern-junior, mid · topic: Component state and data flow (effects) · stacks: react-typescript, nextjs, react-node

**The interviewer asks**

> This component works, but a reviewer has asked you to change it. What is wrong with it?

**Setup the candidate is given**

> ```jsx
> function Cart({ items }) {
>   const [total, setTotal] = useState(0);
>
>   useEffect(() => {
>     setTotal(items.reduce((sum, item) => sum + item.price, 0));
>   }, [items]);
>
>   return <p>Total: ₦{total}</p>;
> }
> ```

**What a strong answer covers** — the answer key; never shown to a candidate

- The total is derived from props, so it is not state at all — compute it during render.
- The effect runs after render, so the user sees the old total for one frame.
- It costs an extra render every time `items` changes.
- It creates a second place for the truth to live, which can disagree with `items`.
- Effects are for synchronising with things outside React, not for keeping values in step.

**Rubric: Diagnosing an unnecessary effect** (`effect-diagnosis`)

**Identifies what is wrong — 40%**

That the value is derived and does not need to be state, or that the effect duplicates a render.

- **0 (absent):** Sees nothing wrong.
- **1 (weak):** Locates the problem somewhere else — the dependency array, a render loop — whatever else is said about it.
- **2 (partial):** Identifies the effect as suspicious but explains it as a style preference.
- **3 (solid):** Says that the value can be computed during render, so it is not state.
- **4 (excellent):** As 3, and states the rule: effects are for synchronising with things outside React.

_Asked for by the opening prompt; no planned follow-up._

**Explains the consequence — 30%**

An extra render, a frame of stale UI, and a second place for the value to go wrong.

- **0 (absent):** No consequence given.
- **1 (weak):** A consequence that does not follow — "it is slower" with nothing behind it, or an account of a runaway loop this code does not have.
- **2 (partial):** Mentions an extra render without saying why it happens.
- **3 (solid):** Explains that the effect runs after render, so the user briefly sees the old value.
- **4 (excellent):** As 3, and notes that the state can now disagree with the props it came from.

_Planned follow-up — asked only if the answer has not already covered this:_

> What does the user actually see because of that?

**Proposes the simpler version — 30%**

Removes the state and the effect, computing the value where it is used.

- **0 (absent):** No alternative offered.
- **1 (weak):** Keeps the state and the effect and adds machinery around them — a new dependency array, a memo, an equality guard.
- **2 (partial):** Removes the effect but keeps the redundant state.
- **3 (solid):** Computes during render; the state and the effect both disappear.
- **4 (excellent):** As 3, and says what they would do if the calculation really were expensive — measure it first, rather than assume.

_Planned follow-up — asked only if the answer has not already covered this:_

> How would you write it instead?

> **The drafter is unsure about:** This is the clearest "one right answer" question in the bank, which makes it good for calibration but weak at separating a solid candidate from an excellent one. The excellence descriptors lean on naming the rule and on memoisation — is that the right bar, or would you rather see them notice the one-frame-stale UI? The top of criterion 3 no longer rewards knowing when to memoise, because rewarding that teaches juniors to reach for `useMemo` in interviews, which is the habit an interviewer here said they spend most of their time undoing. "What does it actually cost" is now "what does the user actually see", because spoken aloud the first version was vague — cost in milliseconds, in money, in maintenance? Tagged React + Next.js and React + Node: the candidate is shown JSX with `useState` and `useEffect`, so it would be meaningless to anyone on Vue, Angular or vanilla JS — but it reads the same for a full-stack candidate writing that component as for a frontend one.

### 6. css-overflow-at-360

**technical** · difficulty 2/5 · roles: frontend, fullstack · intern-junior · topic: CSS layout and responsive design (responsive debugging)

**The interviewer asks**

> A tester reports that on their phone the page scrolls sideways — there is a strip of empty space to the right of everything. It looks fine on your laptop. How do you find what is causing it?

- Reproduce it first at a narrow width (360px) in the device toolbar, rather than guessing.

- Usual suspects — a fixed width, a flex or grid child that will not shrink below its content, a wide table or image, a long unbroken string, negative margins.
- Fix the cause; `overflow-x: hidden` hides the symptom and usually hides a real bug.
- Prefer a fix that holds at every width over a media query for one size.

**Rubric: Diagnosing a layout that breaks on a phone** (`responsive-layout-diagnosis`)

**Finds the cause methodically — 40%**

Narrows down to the element that is too wide rather than guessing at fixes — for example by using the inspector, or by bisecting the page.

- **0 (absent):** Starts changing CSS at random.
- **1 (weak):** Applies a fix to a cause they never confirmed, however specific the hunch — searching the stylesheet for one suspect property rather than reproducing the overflow.
- **2 (partial):** Uses the inspector but stops at the first element that looks wrong.
- **3 (solid):** Identifies the specific element that exceeds the viewport and says how they found it.
- **4 (excellent):** As 3, with a repeatable method (device toolbar at 360px, then narrowing down the subtree).

_Asked for by the opening prompt; no planned follow-up._

**Knows the usual suspects — 30%**

Fixed widths, long unbroken strings, wide tables and images, negative margins, `100vw` with a scrollbar.

- **0 (absent):** No candidate causes.
- **1 (weak):** One cause, stated as the usual answer — including `100vw` beside a scrollbar, which is not what happens on a phone.
- **2 (partial):** Two or three causes, unsorted.
- **3 (solid):** Several plausible causes, with a reason for checking one first.
- **4 (excellent):** As 3, including a cause that is easy to miss (overflowing text, or a `min-width: auto` flex item).

_Planned follow-up — asked only if the answer has not already covered this:_

> What would you expect the culprit to turn out to be?

**Fixes without breaking wider screens — 30%**

A fix that holds from 360px upward, rather than a media query patching one width.

- **0 (absent):** No fix, or one that would break other sizes.
- **1 (weak):** Hides the symptom (`overflow-x: hidden` on the page) without addressing the cause — including when it is offered as standard practice.
- **2 (partial):** A media query for small screens only.
- **3 (solid):** A fix that works at every width (fluid sizing, wrapping, `max-width: 100%`).
- **4 (excellent):** As 3, and says how they would check it stays fixed — a test or a screenshot at 360px.

_Planned follow-up — asked only if the answer has not already covered this:_

> How would you fix it?

It belongs in a follow-up about the laptop, if anywhere.

### 7. slow-page-on-3g

**scenario** · difficulty 3/5 · roles: frontend, fullstack · intern-junior, mid · topic: Browser rendering and performance (performance investigation)

**The interviewer asks**

> A user writes in: "your site takes forever to load on my phone". You cannot reproduce it — on your laptop the page appears instantly. Before you change anything, how would you see what they are seeing?

**What a strong answer covers** — the answer key; never shown to a candidate

- Ask for what the report is missing — which page, which device, on mobile data or wifi, every time or once.
- Reproduce under the user's conditions — throttle the network to Slow 4G and the CPU 4–6×.
- Record a load and read it — the waterfall for bytes and round trips, the main thread for long tasks.
- Decide which budget is blown, network or CPU, before choosing a fix.
- Make the change the measurement points to, then measure again to see whether it helped.

**Rubric: Investigating a slow page** (`performance-investigation`)

**Measures before changing — 40%**

## Track: Frontend engineer — intern and junior

`frontend-intern-junior` · frontend · intern-junior

**Topics covered** (core topics drive the readiness score): JavaScript fundamentals **(core)**, Component state and data flow **(core)**, Browser rendering and performance **(core)**, CSS layout and responsive design **(core)**, HTTP, APIs and the network **(core)**, Debugging and diagnosis **(core)**, Working with a team **(core)**, Accessibility **(core)**, Testing frontend code **(core)**, Saying it in writing, Talking about your own work

### JavaScript in the browser you ship to

The runtime your code lives in, and the network it depends on.

#### How your JavaScript actually runs

`how-javascript-runs` · 12 min

Your page has **one thread** for running JavaScript, and that same thread paints the
screen. Everything follows from that.

When a function is called it goes on the **call stack**. The browser runs it to
completion — nothing else happens in that page while it does. A loop that takes 300ms
is 300ms in which no button responds and no frame is drawn. This is why "the page
froze" is usually not the network.

Work that finishes later does not interrupt the running code. It waits in a queue:

- **Tasks** (also called macrotasks): `setTimeout`, a click, a `fetch` response
  arriving.
- **Microtasks**: promise callbacks — `.then`, and everything after an `await`.

After the stack empties, the browser drains **all** microtasks, then takes one task,
then considers painting. So a promise chain that never stops queueing more microtasks
can starve rendering just as effectively as a long loop.

```js
console.log("1");
setTimeout(() => console.log("4"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("2");
```

The order is 1, 2, 3, 4. `setTimeout(…, 0)` does not mean "now" — it means "after the
current work and after the microtasks".

Two practical consequences:

1. **Long work belongs off the main thread** or broken into pieces. On a mid-range
   Android phone the main thread is the scarce resource, not bandwidth.
2. **`await` does not block anything but the function it is in.** The rest of the page
   carries on. Two independent requests should be started together and awaited
   together (`Promise.all`), not one after the other.

#### Fetching data, and what happens when it fails

`data-over-the-network` · 12 min

The happy path is the easy half. On a Nigerian mobile network your page will meet slow
responses, dropped connections and captive portals that return HTML where you expected
JSON — and the difference between a junior and a mid-level engineer is usually how
much of that they thought about.

**`fetch` only rejects when the request could not be made at all.** A 404 or a 500 is a
_successful_ fetch with an unhappy status. This is the single most common mistake in
frontend error handling:

```js
const response = await fetch(url);
if (!response.ok) throw new Error(`HTTP ${response.status}`); // without this, a 500
const data = await response.json(); // becomes a parse error
```

**Every screen that loads data has four states**, and all four need a design: loading,
empty ("no jobs match this filter" is not an error), error, and data. A spinner that
never resolves is a bug with no error message.

**Give requests a deadline.** A phone that has lost signal does not fail fast; it hangs.
`AbortController` plus a timer turns that into an error you can show and a retry the
user can choose.

**Retry carefully.** Retrying a `GET` is usually safe. Retrying a payment because the
response did not arrive can take money twice — that is why the API gives you an
idempotency key. When in doubt, ask, and say so in the interview.

Finally: show _something_ useful while waiting. A skeleton that matches the shape of
the content beats a spinner, because the page does not jump when the data lands.

- [ ] the lessons above are accurate, current, and worth a junior's time

### React that stays predictable

Where data lives, and why most effects are a mistake.

#### Where state should live

`where-state-lives` · 12 min

Most confusing React components are confusing because the same fact is stored in two
places. The cure is a habit, not a library.

**Start local.** State belongs in the component that uses it. A dropdown's open/closed
flag has no business above the dropdown.

**Lift only when two components need the same fact.** Move it to their nearest common
parent and pass it down. If that parent is far away and the props have to travel
through components that do not care, that is the moment to reach for context or a
store — not before.

**Derive, do not duplicate.** If `fullName` is `firstName + " " + lastName`, it is not
state; it is a calculation you do while rendering. Storing it means two things to keep
in step, and they will drift.

```jsx
// no
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce(sum, 0)), [items]);

// yes
const total = items.reduce(sum, 0);
```

**Server data is not UI state.** A list of jobs fetched from an API is a _cache_ of
something that lives elsewhere: it can be stale, it can fail, it needs refetching. Copying
it into `useState` and editing it by hand is how lists get out of step with the server.
This is what TanStack Query and friends exist for.

**The URL is state too.** A filter, a page number, a selected tab: putting them in the
URL means a candidate can share a link, reload without losing their place, and use the
back button. It costs nothing and interviewers notice.

#### Effects you probably do not need

`effects-you-do-not-need` · 10 min

`useEffect` is for synchronising with something **outside** React — the network, a
timer, a subscription, the document title, a map widget. Almost every other use of it
is a bug waiting to happen, because an effect runs _after_ render, which means the user
sees one frame of the wrong thing first.

Three patterns worth recognising, because interviewers ask about all three:

**1. Deriving state in an effect.** If it can be calculated during render, calculate it
during render. An effect that calls `setState` from props causes a second render every
time.

**2. Reacting to an event in an effect.** If something should happen _because the user
clicked_, do it in the click handler. An effect watching a state variable cannot tell
"the user did this" from "this arrived from the server", and it will fire in cases you
did not intend.

**3. Fetching on mount without cleanup.** Two requests race, the slower one lands last,
and the screen shows the older answer. Either use a data library, or abort the previous
request in the cleanup function:

```jsx
useEffect(() => {
  const controller = new AbortController();
  load(id, controller.signal).then(setJob).catch(ignoreAbort);
  return () => controller.abort();
}, [id]);
```

A good answer in an interview names the cleanup function and says what it is for. A very
good one mentions that in development React mounts components twice on purpose, exactly
so that missing cleanup shows up on your machine rather than on a user's.

### Fast on a mid-range Android phone

What actually costs time, and how to find out rather than guess.

#### What actually makes a page slow

`what-makes-a-page-slow` · 12 min

"It feels slow" is not a diagnosis. There are two different budgets, and they fail
differently.

**The network budget** is bytes and round trips. It hurts most on a first visit, on 3G,
and on a data plan people pay for by the megabyte. Watch: total transferred size, how
many requests block the first paint, and whether anything large is downloaded before the
page is usable.

**The CPU budget** is time on that one main thread. It hurts on every visit. A phone
that costs ₦150,000 has perhaps a quarter of the single-core speed of a development
laptop, so 200ms of JavaScript parsing and execution on your machine is closer to a
second on the device your users hold. Big JavaScript bundles cost twice: once to
download, again to parse and run.

**Measure, then change.** In Chrome DevTools: the Network panel with throttling set to
"Slow 4G", and the Performance panel with CPU throttling at 4–6×. Record a load, then
look at what the main thread was doing. Lighthouse gives you the same picture as a
score, which is useful for tracking but hides which of the two budgets you blew.

The three numbers worth knowing by name:

- **LCP** — when the largest thing on screen finished rendering. Usually an image or a
  heading. Hurt by slow servers, render-blocking CSS and late-loading images.
- **INP** — how long the page takes to respond to a tap. Hurt by long tasks on the main
  thread.
- **CLS** — how much the layout jumped. Hurt by images and ads without reserved space.

An interviewer is not looking for these acronyms. They are looking for someone who
opens a profiler before opening an editor.

#### Images, fonts and the critical path

`images-and-fonts` · 10 min

On most pages the heaviest things are not code. They are images and fonts, and both have
well-known fixes.

**Images.** Serve the size you display: a 2,000px photo scaled to a 360px column wastes
most of what it cost to download. `srcset` and `sizes` let the browser choose. Prefer
modern formats (WebP, AVIF) with a fallback. Always set `width` and `height` — the
browser then reserves the space and the text below does not jump when the image lands.
Use `loading="lazy"` for anything below the fold, and _not_ for the main image, which
you want early.

**Fonts.** A custom font blocks the text that uses it. `font-display: swap` shows the
fallback immediately and swaps when the font arrives — a brief flash of the wrong font
is better than a second of no text at all. Subset to the characters you need, self-host
rather than depend on a third party's uptime, and preload only the one or two files
needed for the first paint.

**The critical path** is everything the browser must fetch and process before it can
paint. CSS is render-blocking by design: the browser will not show a half-styled page.
A synchronous `<script>` in `<head>` blocks parsing entirely — use `defer`. Anything
that is not needed for the first screen (a charting library, a rich editor, a map)
belongs behind a dynamic import, loaded when the user actually needs it.

The habit to build: before adding a dependency, ask what it costs on a phone. Most
"small" packages are not.
