### 1. js-async-ordering

**technical** · difficulty 3/5 · intern-junior, mid · topic: JavaScript fundamentals (event loop)

**The interviewer asks**

> Have a look at this snippet. In what order do the four numbers appear in the console, and what is it about the way the browser runs JavaScript that makes it come out that way?

**Setup the candidate is given**

> ```js
> console.log("1");
> setTimeout(() => console.log("4"), 0);
> Promise.resolve().then(() => console.log("3"));
> console.log("2");
> ```

**What a strong answer covers** — the answer key; never shown to a candidate

- The order is 1, 2, 3, 4.
- JavaScript runs on one thread; the synchronous lines run to completion first.
- Promise callbacks are microtasks and are drained after the current work, before the next task.
- A zero-delay `setTimeout` is a task, so it waits behind the microtasks — "0ms" is not "now".
- The same thread paints, so long synchronous work blocks rendering and input.

**Rubric: Understanding of asynchronous ordering** (`async-ordering-understanding`)

**Gets the order right — 30%**

Predicts the actual output order of the snippet.

- **0 (absent):** No answer, or an order with no reasoning behind it.
- **1 (weak):** Order is wrong in a way that shows no model of queuing (e.g. purely top to bottom).
- **2 (partial):** Synchronous lines placed correctly; the promise and the timer are swapped.
- **3 (solid):** Correct order.
- **4 (excellent):** Correct order, stated confidently, with the ambiguous case (a zero-delay timer) called out.

**Explains the mechanism — 45%**

Why that order: one thread, a call stack that runs to completion, microtasks drained before the next task. Not a memorised rule ("promises are faster").

- **0 (absent):** No explanation offered.
- **1 (weak):** A rule with no mechanism ("promises come first").
- **2 (partial):** Mentions the event loop or a queue, but conflates timers and promise callbacks.
- **3 (solid):** Distinguishes tasks from microtasks and says when each is taken.
- **4 (excellent):** As 3, and explains that the stack must empty first, so `setTimeout(…, 0)` means "not before then".

**Connects it to the user — 25%**

What this means on screen — a frozen page, a late paint, a race between two requests.

- **0 (absent):** Treats it as trivia with no consequence.
- **1 (weak):** Says it "matters for performance" without saying how.
- **2 (partial):** Names one consequence in general terms.
- **3 (solid):** Gives a concrete consequence, such as a long task blocking a tap or a paint.
- **4 (excellent):** As 3, plus what they would do about it (break up work, start requests together).

> **The drafter is unsure about:** Difficulty 3 is a judgement call: plenty of good juniors have never heard the word microtask, and we may be rewarding people who have read a blog post rather than people who can build. Is this a fair question for an intern, or should it be mid only? If it stays, is criterion 3 ("connects it to the user") the right way to stop it being trivia?

### 2. fetch-failure-states

**technical** · difficulty 2/5 · intern-junior · topic: HTTP, APIs and the network (error handling)

**The interviewer asks**

- **3 (solid):** All four states, with empty and error clearly different.
- **4 (excellent):** All four, plus what the user can do from the error state (retry, go back, contact support).

**Handles HTTP errors correctly — 40%**

Knows that `fetch` resolves for a 404 or a 500 and that the status must be checked — the single most common mistake in this area.

- **0 (absent):** No error handling at all.

### 4. react-unnecessary-effect

**technical** · difficulty 3/5 · intern-junior, mid · topic: React state and data flow (effects)

**The interviewer asks**

> This component works, but a reviewer has asked you to change it. What would you say is wrong with it, what does it actually cost, and how would you write it instead?

**Setup the candidate is given**

> ```jsx
> function Cart({ items }) {
>   const [total, setTotal] = useState(0);
>
>   useEffect(() => {
>     setTotal(items.reduce((sum, item) => sum + item.price, 0));
>   }, [items]);
>
>   return <p>Total: ₦{total}</p>;
> }
> ```

**What a strong answer covers** — the answer key; never shown to a candidate

- The total is derived from props, so it is not state at all — compute it during render.
- The effect runs after render, so the user sees the old total for one frame.
- It costs an extra render every time `items` changes.
- It creates a second place for the truth to live, which can disagree with `items`.
- Effects are for synchronising with things outside React, not for keeping values in step.

**Rubric: Diagnosing an unnecessary effect** (`effect-diagnosis`)

**Identifies what is wrong — 40%**

That the value is derived and does not need to be state, or that the effect duplicates a render.

- **0 (absent):** Sees nothing wrong.
- **1 (weak):** Says it "looks off" without locating the problem.
- **2 (partial):** Identifies the effect as suspicious but explains it as a style preference.
- **3 (solid):** Says plainly that the value can be computed during render, so it is not state.
- **4 (excellent):** As 3, and states the rule: effects are for synchronising with things outside React.

**Explains the consequence — 30%**

An extra render, a frame of stale UI, and a second place for the value to go wrong.

- **0 (absent):** No consequence given.
- **1 (weak):** "It is slower", with nothing behind it.
- **2 (partial):** Mentions an extra render without saying why it happens.
- **3 (solid):** Explains that the effect runs after render, so the user briefly sees the old value.
- **4 (excellent):** As 3, and notes that the state can now disagree with the props it came from.

**Proposes the simpler version — 30%**

Removes the state and the effect, computing the value where it is used.

- **0 (absent):** No alternative offered.
- **1 (weak):** Changes the dependency array and keeps the effect.
- **2 (partial):** Removes the effect but keeps the redundant state.
- **3 (solid):** Computes during render; the state and the effect both disappear.
- **4 (excellent):** As 3, and says when memoising would be justified — and that it usually is not.

> **The drafter is unsure about:** This is the clearest "one right answer" question in the bank, which makes it good for calibration but weak at separating a solid candidate from an excellent one. The excellence descriptors lean on naming the rule and on memoisation — is that the right bar, or would you rather see them notice the one-frame-stale UI?

**Topics covered** (core topics drive the readiness score): JavaScript fundamentals **(core)**, React state and data flow **(core)**, Browser rendering and performance **(core)**, CSS layout and responsive design **(core)**, HTTP, APIs and the network **(core)**, Debugging and diagnosis **(core)**, Working with a team **(core)**, Accessibility, Testing frontend code

### JavaScript in the browser you ship to

The runtime your code lives in, and the network it depends on.

#### How your JavaScript actually runs

`how-javascript-runs` · 12 min

Your page has **one thread** for running JavaScript, and that same thread paints the
screen. Everything follows from that.

When a function is called it goes on the **call stack**. The browser runs it to
completion — nothing else happens in that page while it does. A loop that takes 300ms
is 300ms in which no button responds and no frame is drawn. This is why "the page
froze" is usually not the network.

Work that finishes later does not interrupt the running code. It waits in a queue:

- **Tasks** (also called macrotasks): `setTimeout`, a click, a `fetch` response
  arriving.
- **Microtasks**: promise callbacks — `.then`, and everything after an `await`.

After the stack empties, the browser drains **all** microtasks, then takes one task,
then considers painting. So a promise chain that never stops queueing more microtasks
can starve rendering just as effectively as a long loop.

```js
console.log("1");
setTimeout(() => console.log("4"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("2");
```

The order is 1, 2, 3, 4. `setTimeout(…, 0)` does not mean "now" — it means "after the
current work and after the microtasks".

Two practical consequences:

1. **Long work belongs off the main thread** or broken into pieces. On a mid-range
   Android phone the main thread is the scarce resource, not bandwidth.
2. **`await` does not block anything but the function it is in.** The rest of the page
   carries on. Two independent requests should be started together and awaited
   together (`Promise.all`), not one after the other.

#### Fetching data, and what happens when it fails

`data-over-the-network` · 12 min

The happy path is the easy half. On a Nigerian mobile network your page will meet slow
responses, dropped connections and captive portals that return HTML where you expected
JSON — and the difference between a junior and a mid-level engineer is usually how
much of that they thought about.

**`fetch` only rejects when the request could not be made at all.** A 404 or a 500 is a
_successful_ fetch with an unhappy status. This is the single most common mistake in
frontend error handling:

```js
const response = await fetch(url);
if (!response.ok) throw new Error(`HTTP ${response.status}`); // without this, a 500
const data = await response.json(); // becomes a parse error
```

**Every screen that loads data has four states**, and all four need a design: loading,
empty ("no jobs match this filter" is not an error), error, and data. A spinner that
never resolves is a bug with no error message.

**Give requests a deadline.** A phone that has lost signal does not fail fast; it hangs.
`AbortController` plus a timer turns that into an error you can show and a retry the
user can choose.

**Retry carefully.** Retrying a `GET` is usually safe. Retrying a payment because the
response did not arrive can take money twice — that is why the API gives you an
idempotency key. When in doubt, ask, and say so in the interview.

Finally: show _something_ useful while waiting. A skeleton that matches the shape of
the content beats a spinner, because the page does not jump when the data lands.

### React that stays predictable

Where data lives, and why most effects are a mistake.

#### Where state should live

`where-state-lives` · 12 min

Most confusing React components are confusing because the same fact is stored in two
places. The cure is a habit, not a library.

**Start local.** State belongs in the component that uses it. A dropdown's open/closed
flag has no business above the dropdown.

**Lift only when two components need the same fact.** Move it to their nearest common
parent and pass it down. If that parent is far away and the props have to travel
through components that do not care, that is the moment to reach for context or a
store — not before.

**Derive, do not duplicate.** If `fullName` is `firstName + " " + lastName`, it is not
state; it is a calculation you do while rendering. Storing it means two things to keep
in step, and they will drift.

```jsx
// no
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce(sum, 0)), [items]);

// yes
const total = items.reduce(sum, 0);
```

**Server data is not UI state.** A list of jobs fetched from an API is a _cache_ of
something that lives elsewhere: it can be stale, it can fail, it needs refetching. Copying
it into `useState` and editing it by hand is how lists get out of step with the server.
This is what TanStack Query and friends exist for.

**The URL is state too.** A filter, a page number, a selected tab: putting them in the
URL means a candidate can share a link, reload without losing their place, and use the
back button. It costs nothing and interviewers notice.

#### Effects you probably do not need

`effects-you-do-not-need` · 10 min

`useEffect` is for synchronising with something **outside** React — the network, a
timer, a subscription, the document title, a map widget. Almost every other use of it
is a bug waiting to happen, because an effect runs _after_ render, which means the user
sees one frame of the wrong thing first.

Three patterns worth recognising, because interviewers ask about all three:

**1. Deriving state in an effect.** If it can be calculated during render, calculate it
during render. An effect that calls `setState` from props causes a second render every
time.

**2. Reacting to an event in an effect.** If something should happen _because the user
clicked_, do it in the click handler. An effect watching a state variable cannot tell
"the user did this" from "this arrived from the server", and it will fire in cases you
did not intend.

**3. Fetching on mount without cleanup.** Two requests race, the slower one lands last,
and the screen shows the older answer. Either use a data library, or abort the previous
request in the cleanup function:

```jsx
useEffect(() => {
  const controller = new AbortController();
  load(id, controller.signal).then(setJob).catch(ignoreAbort);
  return () => controller.abort();
}, [id]);
```

A good answer in an interview names the cleanup function and says what it is for. A very
good one mentions that in development React mounts components twice on purpose, exactly
so that missing cleanup shows up on your machine rather than on a user's.

### Fast on a mid-range Android phone

What actually costs time, and how to find out rather than guess.

#### What actually makes a page slow

`what-makes-a-page-slow` · 12 min

"It feels slow" is not a diagnosis. There are two different budgets, and they fail
differently.

**The network budget** is bytes and round trips. It hurts most on a first visit, on 3G,
and on a data plan people pay for by the megabyte. Watch: total transferred size, how
many requests block the first paint, and whether anything large is downloaded before the
page is usable.

**The CPU budget** is time on that one main thread. It hurts on every visit. A phone
that costs ₦150,000 has perhaps a quarter of the single-core speed of a development
laptop, so 200ms of JavaScript parsing and execution on your machine is closer to a
second on the device your users hold. Big JavaScript bundles cost twice: once to
download, again to parse and run.

**Measure, then change.** In Chrome DevTools: the Network panel with throttling set to
"Slow 4G", and the Performance panel with CPU throttling at 4–6×. Record a load, then
look at what the main thread was doing. Lighthouse gives you the same picture as a
score, which is useful for tracking but hides which of the two budgets you blew.

The three numbers worth knowing by name:

- **LCP** — when the largest thing on screen finished rendering. Usually an image or a
  heading. Hurt by slow servers, render-blocking CSS and late-loading images.
- **INP** — how long the page takes to respond to a tap. Hurt by long tasks on the main
  thread.
- **CLS** — how much the layout jumped. Hurt by images and ads without reserved space.

An interviewer is not looking for these acronyms. They are looking for someone who
opens a profiler before opening an editor.

#### Images, fonts and the critical path

`images-and-fonts` · 10 min

On most pages the heaviest things are not code. They are images and fonts, and both have
well-known fixes.

**Images.** Serve the size you display: a 2,000px photo scaled to a 360px column wastes
most of what it cost to download. `srcset` and `sizes` let the browser choose. Prefer
modern formats (WebP, AVIF) with a fallback. Always set `width` and `height` — the
browser then reserves the space and the text below does not jump when the image lands.
Use `loading="lazy"` for anything below the fold, and _not_ for the main image, which
you want early.

**Fonts.** A custom font blocks the text that uses it. `font-display: swap` shows the
fallback immediately and swaps when the font arrives — a brief flash of the wrong font
is better than a second of no text at all. Subset to the characters you need, self-host
rather than depend on a third party's uptime, and preload only the one or two files
needed for the first paint.

**The critical path** is everything the browser must fetch and process before it can
paint. CSS is render-blocking by design: the browser will not show a half-styled page.
A synchronous `<script>` in `<head>` blocks parsing entirely — use `defer`. Anything
that is not needed for the first screen (a charting library, a rich editor, a map)
belongs behind a dynamic import, loaded when the user actually needs it.

The habit to build: before adding a dependency, ask what it costs on a phone. Most
"small" packages are not.
